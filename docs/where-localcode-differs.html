Where localcode differs

localcode runs several models against one task and requires all of them to approve the result, books work for a stated time instead of running it now, and validates a multi-agent plan before spending anything on it. This page lists the capabilities that are not standard in coding agents, with the use case each one exists for.

Bottom line

Thirteen capabilities, in two parts. Part 1 is what a single task can be; part 2 is what working in localcode is like day to day. Three of them change the shape of the work itself:

  • Adversarial review across models — up to three reviewers, each on a different model, each in its own session, all of which must approve before the loop ends.
  • Time-shifted work — a prompt naming a time is booked rather than run, with the time parsed by localcode instead of the model.
  • Plans validated before execution — a multi-agent plan is authored as structured data and rejected in full if any stage would not work.

The rest cover cost, auditability, running on models you host yourself, and several front ends over one daemon.

Part 1

What a single task can be

1. A decision you do not want one model to make alone

Debate

One model reviewing its own work agrees with itself. Debate puts the work in front of reviewers that are different models, running in separate contexts, and does not accept the result until every one of them approves.

Use case — a schema change before it reaches main

/debate girl,tom 5 migrate the session store to the new event schema
  • Author — this conversation's agent, keeping its history and its prompt cache.
  • Reviewers — girl and tom, each on its own model, running at the same time and unable to see each other.
  • Reviewer memory — one sub-session per reviewer per round, so a reviewer in round four still knows what it asked for in round one.
  • Reviewer powers — reading, plus the project's own verify_command from config.json, with no arguments. No writing at all, bash included.
  • Evidence — git diff HEAD where there is a repository, the tool-call list where there is not.
  • Approval — a boolean each reviewer sets. Anything that is not an explicit approval is not one.
  • Termination — unanimous approval, the round budget, or a two-round standoff in which the author called no tool. The closing line names which.

Two design points carry most of the value:

  • Protocol outside the prompt. A model told to repeat a review ten times inside one turn stops at three and reports it is finished. The rounds are counted by localcode, so the count is real.
  • Reviewers that cannot write. A reviewer with write access becomes a second author, and the disagreement that makes the review worth running disappears.

2. Work that belongs to a later time

Scheduled tasks

A long test run at 09:00 tomorrow is not a prompt to send tomorrow at 09:00. State the time and localcode books it.

Use case — an overnight run booked from the prompt box

tomorrow at 9am run the full test suite and summarise only the failures
  • Split — the model separates the time from the work; localcode parses the time.
  • Confirmation — names the moment localcode read, not the words the model passed on.
  • Forms accepted — relative, clock, named, weekday and absolute, in English and in Korean, with a bare hour meaning the nearest one.
  • Refusals by name — a vague time (later) and a repeat (every day) are each refused rather than guessed at.
  • Execution — its own session, under the conversation's workspace and permission switches.
  • Result — a row in the right panel with a light: blinking while waiting, solid for an unread answer, grey once read.
One limit, stated in the product

A booking fires only while localcode is running. A time that passed while it was closed is reported as missed rather than run late, because the request was for a time.

Three entry points: plain language in the prompt box, the clock button under it, or /schedule in 30 minutes run the tests. /show-scheduled-task is the same list in the terminal.

3. A plan that is checked before it is paid for

Orchestrate

Delegation tools let a model hand work to another model. They do not make it keep to a shape it announced. A model that says it will check every finding with three independent reviewers checks the first two and reports. That is not dishonesty: a stated procedure is a request.

Orchestrate makes the plan data. The model authors it by filling in the tool's own input schema, so the whole plan is validated before a token is spent on running it.

Checked before executionRefusal
Every agent named against the roster the turn was admitted withWhole plan, with the reason
Every reference against a stage that really precedes itWhole plan, with the reason
Every count against its ceilingWhole plan, with the reason

Use case — a review where every finding must be verified

  • Stage 1, fan-out — one agent per review dimension over a list.
  • Stage 2, fan-out over findings — N independent copies per finding from stage 1, each declaring the shape it returns.
  • Filter — keep drops every result whose named field is false. This is the adversarial filter, with no expression language anywhere.
  • Stage 3, barrier — sees everything that survived.
  • Report — written by localcode from what happened, not summarised by a model.

Ceilings are refusals rather than truncations, and the permission prompt shows them rather than an estimate it cannot keep:

LimitValue
Stages per plan8
Agent turns per run32
Wall time per stage10 min
Wall time per run30 min

A stage names a role rather than tools, intersected with the agent's own restriction, so a plan can neither hand bash to a reviewer nor widen what an agent may do. Every stage is a synchronous child, so Esc stops the whole run.

4. Reading another conversation from this one

Cross-conversation reference

The model can read the contents of a different session. Write #<name> in a prompt and the named conversation becomes readable: its prompts, its replies, and what its tools returned. Analysis done last week in another session does not have to be repeated, and does not have to be pasted in by hand.

Use case — checking this project against a report written in another session

#S2 has the final report. Check it against the file here.
  • Resolution — by id, exact title, or unambiguous title prefix, including into the archive. A conversation put away last month is still referable.
  • What arrives — the other conversation's transcript, if the model asks for it, through a tool call it makes itself.
  • Not spliced — not one byte of the named conversation enters the message. The reference becomes localcode's own line saying the contents can be read with a tool.
  • Trust class — the transcript arrives as a tool result: the least trusted class, which is correct for a mixture of somebody else's typing, a model's words, fetched pages and MCP output.
  • Consequence — a #S3 written inside the referenced conversation cannot resolve, and a /permission-skip-all on inside it cannot reach the router. A tool result never re-enters the message path.
  • Never refused — no match, several matches, or the current conversation each produce a notice and the turn continues.

A conversation belonging to another project is flagged as one, with both directories named. #42 stays an issue number. The right arrow completes a conversation name the same way it completes a command, which is what makes a renamed conversation worth naming well.

5. Fifty files read to answer one question

Smart Agent

Reading a large tree to answer a small question fills the conversation with material nobody needs again. Smart Agent turns the session's model into an orchestrator with six specialists, each in its own session and its own context.

SpecialistWork
exploreFind things
librarianDigest long material
oracleReview
planDecompose
implementMake one self-contained change
verifyRun the build
  • Context cost — fifty files read by a specialist cost the main conversation a paragraph.
  • Model per specialist — worked out from the profiles already in config.json, not named in the build. A profile called smart-quick, smart-balanced or smart-deep pins it by hand.
  • No recursion — no specialist can delegate. This is a tool allowlist, not a line of prompt.
  • Parallelism — TaskBackground and TaskCollect run several at once.

On the 25-instance SWE-bench Verified run in the benchmark, Smart Agent on resolved 21 of 25 against 19 with it off, on the same model. That spread is inside run-to-run variance and does not rank anything; the measured difference that run does support is output tokens, 7,586 against 9,434 per instance.

6. Models you host yourself

Local models and failover

Support for a local endpoint is usually a generic OpenAI-compatible shim. Several things that matter are outside what that shim covers.

ProblemHandling
Reasoning has no field in the OpenAI API, so every runtime invented oneBoth spellings read: reasoning_content (DeepSeek, vLLM, SGLang, LM Studio, llama.cpp, Ollama) and reasoning (OpenRouter and others)
A local server's window is whatever was loaded, not what the model supportsRead from the server: GET /v1/models, or /props on llama.cpp
One GPU serves one request whatever a global concurrency number saysPer-provider max_concurrent_tasks, taken before the daemon-wide slot
A rate limit or an expired credential ends the turnTwo retries on the failing endpoint (1s, 2s), then a per-profile fallback chain with the request re-derived for the new family
A request refused for length ends the turnSummarise, then trim, shrinking until the server accepts it

A 401 or an unknown model id skips the wait, because time does not fix those, and a malformed request retries nowhere.

7. A prompt you can audit

Prompt inventory

The system prompt is assembled from a declared inventory rather than concatenated. Each piece carries a stable id, a source, a trust class saying whether it may be followed as instruction at all, a place in the request, and a condition saying when it applies.

Use case — finding out what is actually being sent

/context        what the next turn would send, with no model call
/context all    and what was left out, and why
/context <id>   the manifest a given model call was built from
  • Reported — what is included and why, per-category token estimates, tool definitions built-in and per MCP server, conversation and reserved output against the window.
  • Flagged — whether the request carries content that may not be followed as instruction.
  • Cost — none. No model call is made to answer it.

The same manifest ids appear in the trace, so a failover that reused the failed model's prompt is visible as an unchanged manifest id on a changed model family.

8. Knowing what a run cost and who did it

Trace

With Smart Agent on, one JSON line per event is written to ~/.localcode/trace/.

  • Recorded — which model answered and on which profile, cost including cache reads and writes, which tool ran and for how long, what was delegated to whom, every failover, every compaction.
  • One trace id per turn, inherited by every sub-agent, so a fan-out to three specialists reads back as one story rather than four unrelated logs.
  • Live — GET /api/trace tails it while the session is open.

9. Commands the model may run

Model-invocable commands

Shipped in v0.83.0, off by default. On, the model may run a built-in, a custom command or a skill itself, each as a turn of its own in the same conversation.

Use case — cleanup the model decides is due

Read the mail. If there is anything from the release manager, run /tidy-context.
  • Two levels — the switch is whether; the list is which, written down separately, so turning the switch off does not discard the choices.
  • Built-ins — named in model_commands with the slash.
  • Custom commands and skills — opt themselves in with model_invocable: true in their own frontmatter.
  • No wildcard — the list reaches /permission-skip-all if you write it, so it must be a name in a file.
  • Shell splices excluded — a command containing a backtick shell splice can never be model-invocable, and the refusal is named rather than silent.
Read before turning this on

The model decides when to run a command from what it has read: files, command output, and whatever an MCP server returned. Anything on the list is reachable from text the model did not write. The switch, the list and the settings note all say so.

Part 2

The clients

One daemon holds every session. What attaches to it is a choice, and more than one thing can attach to the same session at the same time. The screenshots below are of localcode 0.84.0.

Use case — showing a running session to someone else

The daemon serves the interface over HTTP, so a second person who can reach that address opens the same live session: the same transcript, the same running tools, the same permission prompts, updating as it happens. Nothing is exported and no copy is made.

# on the machine running localcode
localcode --headless --listen 127.0.0.1:4096

# on the other person's machine
ssh -L 4096:127.0.0.1:4096 you@your-machine
# then open http://127.0.0.1:4096

The same address also takes a second terminal: localcode --server http://127.0.0.1:4096 attaches a TUI to a session someone else is watching in a browser.

There is no authentication token

Anyone who can reach the listen address gets the entire API, shell execution included. Bind to loopback and share through an SSH tunnel, as above. Do not bind 0.0.0.0 on an untrusted network.

11. The prompt box

Completion and turn navigation

Command completion

Type part of a name and press the right arrow. Skills, custom commands, the daemon's own commands and each client's own commands are all in one list, because they are all invoked the same way and somebody typing /sm is not thinking about which list a name is in.

  • Walking, not guessing — each press offers the next match, and the last stop is the text as typed, so the cycle is never one you cannot leave. Completing to the longest common prefix would be useless here: skills are named for what they do, and the shared prefix of pdf-tools and pptx is one letter.
  • Mid-sentence — a command name completes where it is written, not only at the start of the box. read the mail, then run /tid finishes and leaves the sentence on both sides of it alone.
  • Paths left alone — a slash that does not open a word is not a command, so internal/tui/co and /Users/me/co are ignored.
  • Conversation names too — the same key completes a #<name> reference, spliced into the sentence.
  • Both clients — the same key, the same list, the same count line.

Moving through your own turns

Use case — finding what you asked, forty turns ago

  • Alt + Up and Alt + Down move the view from one of your own turns to the next, skipping everything the model wrote in between. This is how you find a prompt in a session with fifty of them. Browser front end only; the terminal draws the same turn marks but does not bind the keys.
  • Up and Down are separate, and move the text: they recall previous prompts into the box, per conversation. The list is refilled from the transcript when a session opens, so reopening a conversation recalls what was asked in it before.
  • Why two — reading back what you asked and editing what you asked again are different jobs, and one key cannot do both without taking the other away.

Scrolling up holds the view where you put it, however much the model writes underneath, in both clients and in a background task's own window. Following the newest output resumes when you scroll back to the bottom.

Use case — a conversation you are finished with but not done with

  • Still readable — an archived conversation is not a deleted one, which is the point of keeping it.
  • Still written to — a background task that outlives the archive still records that it finished.
  • Still referable — #<name> resolves into the archive, so the conversation you put away last month is exactly the one you can still cite.
  • What it refuses — starting work: a delegation, a background task, a scheduled run. One store-level invariant closes all three at once, rather than a check at each caller.
  • Not forced — archiving is refused while a turn or a background task or a scheduled run is going. Deleting kills that work because the records are going away; archiving has no such excuse.

13. Paths that leave the project

Workspace boundary

A path that leaves the session's own workspace is its own question, separate from whether the tool is allowed at all. Answering "yes, this agent may read files" is not answering "yes, it may read ~/.ssh".

CaseTreatment
An absolute path, or one containing ..Resolved, then judged against the session's workspace
A symlink inside the workspace pointing at ~/.awsOutside. Judged on physical paths, so the link does not launder the destination
A file about to be createdJudged by where its link leads, before it exists
A path that cannot be resolved at allCosts one question, rather than one blind allow
A credential store: .env, *.pem, id_rsa, ~/.ssh, ~/.aws/credentials, .netrcRefused outright with Smart Agent on. Deny class, so no skip unlocks it
A shell command that leaves the workspaceNot covered by these two, and the dialog says so: a shell command is not a path. bash asks on its own terms

Use case — one project, one boundary, several sessions

  • Per session — the boundary is the workspace of the session asking, so two conversations in two projects on one daemon each have their own.
  • Covered — read_file, grep and glob as reading; write_file and edit as writing.
  • Answers available — allow once, allow for this session, allow this directory, or allow outside generally. The remembered ones can be forgotten again with /read-outside mem-clear.
  • From the terminal — /read-outside and /write-outside set the same two switches, and /permission-skip-tools deliberately skips tool prompts while still asking about paths that leave the project.

Parity, not difference

These are deliberately the same as elsewhere, and are listed so the tables above read as a difference rather than a feature count.

  • Undo and clear — /rewind and /clear follow Claude Code's scope on purpose.
  • Project context — AGENTS.md with @path imports and a CLAUDE.md fallback. ~/.claude/CLAUDE.md applies, so an existing setup is reused rather than replaced.
  • MCP — all three transports, and localcode mcp import-claude pulls an existing Claude Code setup.
  • Skills and custom commands — the same directory conventions and progressive disclosure.
  • Tool hooks — pre_tool_use, post_tool_use, user_prompt_submit, stop, session_start.
  • Permissions — allow once, allow for session, always allow, the last written into config.json.
  • Compaction — on demand and automatic past a threshold.
  • Prompt history recall — Up and Down in the prompt box, as in any shell.

Qualifications

  • The comparison column describes a general baseline across coding agents in common use as of 2026-09-01, not a feature audit of any one product. These tools ship frequently, and a capability listed as absent may exist by the time this is read.
  • Part 2 is not uniformly unique. Sharing one live session between front ends, and moving the view between your own turns, are uncommon. Rename, reorder and fork are conveniences that several tools have in some form; they are here because this page is also about what using localcode is like.
  • Every localcode claim is a shipped behaviour at v0.84.0, documented in USAGE.md and covered by the repository's test gate.
  • Benchmark numbers are one run of 25 instances and the spread between agents is inside run-to-run variance. See the benchmark page for what it does and does not support.
  • Two capabilities are marked experimental in the product: the native desktop window, and update-in-place on Windows, which applies but does not restart localcode.
