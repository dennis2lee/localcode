localcode가 다른 점

localcode는 하나의 작업에 여러 모델을 붙여 전원이 승인해야 끝나게 하고, 시각이 적힌 프롬프트를 지금 실행하는 대신 예약하며, 멀티 에이전트 계획을 실행하기 전에 검증합니다. 이 문서는 코딩 에이전트에서 표준이 아닌 기능들을, 각각이 존재하는 이유가 되는 실제 사용 사례와 함께 정리합니다.

결론부터

기능 13가지, 두 부분입니다. 1부는 하나의 작업이 무엇이 될 수 있는가, 2부는 매일 쓰는 경험입니다. 이 중 셋은 작업의 형태 자체를 바꿉니다.

  • 모델 간 교차 검증 — 리뷰어 최대 3개, 각각 다른 모델, 각각 자기 세션. 전원이 승인해야 루프가 끝납니다.
  • 시각을 지정한 작업 — 시각이 적힌 프롬프트는 실행이 아니라 예약됩니다. 시각은 모델이 아니라 localcode가 해석합니다.
  • 실행 전에 검증되는 계획 — 멀티 에이전트 계획을 구조화된 데이터로 작성하게 하고, 한 단계라도 성립하지 않으면 계획 전체를 거절합니다.

나머지는 비용, 감사 가능성, 직접 호스팅하는 모델, 그리고 하나의 데몬 위에 붙는 여러 화면에 관한 것입니다.

기능 비교

오른쪽 열은 특정 제품이 아니라 일반적으로 쓰이는 코딩 에이전트들의 공통 기준선을 서술합니다. 읽는 방법은 전제와 한계를 보십시오.

1. 모델 하나에게 맡기고 싶지 않은 결정

Debate

자기 작업을 스스로 검토하는 모델은 자기 자신에게 동의합니다. Debate는 결과물을 다른 모델인 리뷰어들 앞에 놓고, 각각을 분리된 컨텍스트에서 돌리며, 전원이 승인하기 전에는 결과를 받아들이지 않습니다.

사용 사례 — main에 들어가기 전의 스키마 변경

/debate girl,tom 5 migrate the session store to the new event schema
  • 작성자 — 이 대화의 에이전트. 자기 히스토리와 프롬프트 캐시를 그대로 유지합니다.
  • 리뷰어 — girl과 tom. 각자 자기 모델로, 동시에 실행되며, 서로를 볼 수 없습니다.
  • 리뷰어의 기억 — 리뷰어마다 라운드마다 서브세션 하나. 4라운드의 리뷰어도 1라운드에서 자기가 무엇을 요구했는지 알고 있습니다.
  • 리뷰어의 권한 — 읽기, 그리고 config.json의 verify_command를 인자 없이 실행하는 것까지. 쓰기는 bash를 포함해 일절 없습니다.
  • 근거 — 저장소가 있으면 git diff HEAD, 없으면 도구 호출 목록.
  • 승인 — 리뷰어가 설정하는 불리언 값. 명시적 승인이 아닌 것은 승인이 아닙니다.
  • 종료 — 전원 승인, 라운드 예산 소진, 또는 작성자가 도구를 한 번도 호출하지 않은 채 두 라운드가 지난 교착. 마지막 줄이 어느 쪽인지 밝힙니다.

가치의 대부분은 두 가지 설계 판단에서 나옵니다.

  • 프로토콜을 프롬프트 밖에 둔 것. 한 턴 안에서 리뷰를 열 번 반복하라고 지시받은 모델은 세 번에서 멈추고 다 했다고 보고합니다. 라운드를 세는 주체가 localcode이므로 그 횟수는 실제 횟수입니다.
  • 쓸 수 없는 리뷰어. 쓰기 권한을 가진 리뷰어는 두 번째 작성자가 되고, 리뷰를 할 가치가 있게 만들었던 의견 불일치가 사라집니다.

2. 나중에 해야 하는 일

예약 작업

내일 아침 9시의 긴 테스트 실행은, 내일 아침 9시에 보내야 하는 프롬프트가 아닙니다. 시각을 말하면 localcode가 예약합니다.

사용 사례 — 프롬프트 창에서 예약하는 야간 실행

내일 아침 9시에 전체 테스트 돌리고 실패한 것만 정리해줘
  • 분리 — 모델은 시각과 작업을 분리하고, 시각은 localcode가 해석합니다.
  • 확인 — 모델이 넘긴 말이 아니라, localcode가 읽어낸 시각을 그대로 보여줍니다.
  • 인식하는 형식 — 상대·시계·명명·요일·절대 형식을 한국어와 영어 모두. 조사는 작업이 아니라 시각에 붙는 것으로 처리하고, 시각만 있으면 가장 가까운 그 시각을 뜻합니다.
  • 이름을 대는 거절 — 모호한 시각(나중에)과 반복(매일)은 추측하지 않고 각각 거절합니다.
  • 실행 — 자기 세션에서, 그 대화의 workspace와 권한 스위치를 따라.
  • 결과 — 오른쪽 패널의 행 하나와 표시등. 대기 중에는 깜빡이고, 읽지 않은 답이 있으면 켜지고, 읽으면 회색이 됩니다.
제품이 스스로 밝히는 한계 하나

예약은 localcode가 실행 중일 때만 발동합니다. 꺼져 있는 동안 지나간 시각은 늦게 실행하지 않고 놓쳤다고 보고합니다. 요청이 시각에 대한 것이었기 때문입니다.

들어가는 길은 셋입니다. 프롬프트 창의 평범한 문장, 그 아래의 시계 버튼, 또는 /schedule 30분 뒤 run the tests. 터미널에서는 /show-scheduled-task가 같은 목록입니다.

3. 비용을 치르기 전에 검증되는 계획

Orchestrate

위임 도구는 모델이 다른 모델에게 일을 넘기게 해줍니다. 하지만 모델이 선언한 형태를 지키게 만들지는 못합니다. "모든 발견 사항을 독립적인 리뷰어 셋으로 검증하겠다"고 말한 모델은 앞의 둘만 확인하고 보고합니다. 이건 거짓말이 아닙니다. 서술된 절차는 요청일 뿐입니다.

Orchestrate는 계획을 데이터로 만듭니다. 모델이 도구의 입력 스키마를 채워 계획을 작성하므로, 실행에 토큰을 쓰기 전에 계획 전체가 검증됩니다.

실행 전에 검사되는 것거절 범위
계획이 지명한 모든 에이전트를, 그 턴이 허용된 명단과 대조계획 전체, 이유와 함께
모든 참조를, 실제로 앞서는 단계인지 대조계획 전체, 이유와 함께
모든 개수를, 각각의 상한과 대조계획 전체, 이유와 함께

사용 사례 — 모든 발견 사항을 반드시 검증해야 하는 리뷰

  • 1단계, 팬아웃 — 리뷰 관점 목록에 대해 관점마다 에이전트 하나.
  • 2단계, 발견 사항 위의 팬아웃 — 1단계의 발견 사항마다 독립된 사본 N개. 각각 반환할 형태를 선언합니다.
  • 필터 — keep이 지정된 필드가 false인 결과를 모두 버립니다. 이것이 교차 검증 필터이며, 어디에도 수식 언어는 없습니다.
  • 3단계, 배리어 — 살아남은 전부를 봅니다.
  • 보고서 — 모델의 요약이 아니라, 실제로 일어난 일로부터 localcode가 작성합니다.

상한은 잘라내기가 아니라 거절이며, 권한 확인 창은 지킬 수 없는 추정치 대신 이 값들을 그대로 보여줍니다.

제한값
계획당 단계 수8
실행당 에이전트 턴32
단계당 소요 시간10분
실행당 소요 시간30분

단계는 도구가 아니라 역할을 지정하고, 그 역할은 에이전트 자신의 제한과 교집합을 취합니다. 그래서 계획이 리뷰어에게 bash를 쥐여줄 수도, 에이전트의 권한을 넓힐 수도 없습니다. 모든 단계가 동기 자식이므로 Esc 하나로 전체가 멈춥니다.

4. 이 대화에서 다른 대화를 읽기

다른 대화 참조

모델이 다른 세션의 내용을 읽을 수 있습니다. 프롬프트에 #<이름>이라고 쓰면 그 대화를 읽을 수 있게 됩니다. 그쪽에서 주고받은 프롬프트, 모델의 답변, 도구가 반환한 내용까지요. 지난주 다른 세션에서 한 분석을 다시 할 필요도, 손으로 붙여넣을 필요도 없습니다.

사용 사례 — 다른 세션에서 작성한 보고서와 이 프로젝트를 대조

#S2 has the final report. Check it against the file here.
  • 해석 — id, 정확한 제목, 또는 모호하지 않은 제목 접두사로. 보관함 안까지 찾습니다. 지난달에 치워둔 대화도 여전히 참조할 수 있습니다.
  • 실제로 도착하는 것 — 모델이 요청하면, 자신이 호출한 도구를 통해 그 대화의 전사가 도착합니다.
  • 붙여넣지 않음 — 지목된 대화의 내용은 단 한 바이트도 메시지에 들어가지 않습니다. 참조는 "이 대화의 내용은 도구로 읽을 수 있다"는 localcode 자신의 한 줄이 됩니다.
  • 신뢰 등급 — 전사는 도구 결과로 도착합니다. 가장 낮은 등급이고, 남의 입력·모델의 말·가져온 웹 페이지·MCP 출력이 섞인 것에는 그게 맞는 등급입니다.
  • 따라오는 결과 — 참조된 대화 안에 적힌 #S3는 해석되지 않고, 그 안의 /permission-skip-all on은 라우터에 닿지 못합니다. 도구 결과는 절대 메시지 경로로 되돌아가지 않기 때문입니다.
  • 거절하지 않음 — 일치 없음, 여러 개 일치, 지금 있는 대화를 가리킨 경우 모두 안내만 남기고 턴은 계속됩니다.

다른 프로젝트에 속한 대화는 그렇다고 표시되고 양쪽 디렉터리를 함께 알려줍니다. #42는 여전히 이슈 번호입니다. 오른쪽 방향키가 명령을 완성하듯 대화 이름도 완성해 주는데, 이 때문에 대화 이름을 잘 지어둘 값어치가 생깁니다.

5. 질문 하나에 답하려고 읽은 파일 50개

Smart Agent

작은 질문에 답하려고 큰 트리를 읽으면, 다시 볼 일 없는 자료로 대화가 가득 찹니다. Smart Agent는 세션의 모델을 오케스트레이터로 바꾸고, 각자 자기 세션과 자기 컨텍스트를 가진 전문가 여섯을 붙여줍니다.

전문가맡는 일
explore찾기
librarian긴 자료 소화하기
oracle검토하기
plan분해하기
implement자족적인 변경 하나 만들기
verify빌드 돌리기
  • 컨텍스트 비용 — 전문가가 읽은 파일 50개가 본 대화에서는 한 문단 값입니다.
  • 전문가별 모델 — 빌드에 박아 넣는 게 아니라 이미 config.json에 있는 프로파일로부터 결정됩니다. smart-quick, smart-balanced, smart-deep이라는 이름의 프로파일이 있으면 손으로 고정됩니다.
  • 재귀 없음 — 어떤 전문가도 위임할 수 없습니다. 프롬프트 한 줄이 아니라 도구 허용 목록으로 막습니다.
  • 병렬 — TaskBackground와 TaskCollect가 여러 개를 동시에 돌립니다.

벤치마크의 SWE-bench Verified 25개 실행에서, 같은 모델로 Smart Agent를 켰을 때 25개 중 21개, 껐을 때 19개를 해결했습니다. 이 차이는 실행 간 편차 안에 있어 순위를 매기지 못합니다. 그 실행이 실제로 뒷받침하는 측정값은 인스턴스당 출력 토큰으로, 7,586 대 9,434입니다.

6. 직접 호스팅하는 모델

로컬 모델과 페일오버

로컬 엔드포인트 지원은 보통 범용 OpenAI 호환 껍데기 하나로 끝납니다. 정작 중요한 것 몇 가지가 그 껍데기 바깥에 있습니다.

문제처리
OpenAI API에는 reasoning을 담을 필드가 없어서 런타임마다 필드를 새로 만들었다두 철자를 모두 읽음. reasoning_content(DeepSeek, vLLM, SGLang, LM Studio, llama.cpp, Ollama)와 reasoning(OpenRouter 등)
로컬 서버의 컨텍스트 창은 모델의 사양이 아니라 실제로 로드된 값이다서버에 물어봄. GET /v1/models, llama.cpp는 /props
전역 동시성 숫자가 무엇이든 GPU 하나는 요청 하나를 처리한다provider별 max_concurrent_tasks를 데몬 전역 슬롯보다 먼저 적용
요청 한도나 만료된 자격증명이 턴을 끝내버린다실패한 엔드포인트에 두 번 재시도(1초, 2초) 후, 프로파일별 fallback 체인으로. 새 계열에 맞게 요청을 다시 구성
길이 초과로 거절된 요청이 턴을 끝내버린다요약하고, 그래도 모자라면 잘라내며, 서버가 받아들일 때까지 줄임

401이나 없는 모델 id는 대기를 건너뜁니다. 시간이 해결해 주는 문제가 아니기 때문입니다. 형식이 잘못된 요청은 어디에도 재시도하지 않습니다.

7. 감사할 수 있는 프롬프트

프롬프트 인벤토리

시스템 프롬프트는 이어 붙이는 게 아니라 선언된 인벤토리에서 조립됩니다. 각 조각은 고정된 id, 출처, 지시로 따라도 되는지를 말하는 신뢰 등급, 요청 안에서의 위치, 그리고 언제 적용되는지를 말하는 조건을 갖습니다.

사용 사례 — 실제로 무엇이 전송되는지 확인하기

/context        다음 턴이 보낼 것. 모델 호출 없음
/context all    빠진 것과 그 이유까지
/context <id>   특정 모델 호출이 무엇으로 만들어졌는지
  • 보고 내용 — 무엇이 왜 포함됐는지, 범주별 토큰 추정치, 내장 및 MCP 서버별 도구 정의, 컨텍스트 창 대비 대화와 예약된 출력량.
  • 표시 — 지시로 따라서는 안 되는 내용이 요청에 실려 있는지 여부.
  • 비용 — 없음. 이 답을 만들기 위한 모델 호출을 하지 않습니다.

같은 매니페스트 id가 트레이스에도 나타납니다. 그래서 실패한 모델의 프롬프트를 그대로 재사용한 페일오버는, 모델 계열이 바뀌었는데 매니페스트 id가 그대로인 형태로 드러납니다.

8. 무엇이 얼마를 썼고 누가 했는지

트레이스

Smart Agent가 켜져 있으면 일어난 일마다 JSON 한 줄이 ~/.localcode/trace/에 기록됩니다.

  • 기록되는 것 — 어떤 모델이 어떤 프로파일로 답했는지, 캐시 읽기·쓰기를 포함한 비용, 어떤 도구가 얼마나 걸렸는지, 무엇을 누구에게 위임했는지, 모든 페일오버, 모든 압축.
  • 턴당 trace id 하나가 모든 서브 에이전트에 상속됩니다. 전문가 셋으로 팬아웃한 작업이 무관한 로그 넷이 아니라 하나의 이야기로 읽힙니다.
  • 실시간 — 세션이 열려 있는 동안 GET /api/trace가 꼬리를 따라갑니다.

9. 모델이 실행할 수 있는 명령

모델이 실행하는 명령

v0.83.0에 들어갔고 기본은 꺼짐입니다. 켜면 모델이 내장 명령, 커스텀 명령, 스킬을 직접 실행할 수 있고, 각각 같은 대화 안에서 자기 턴으로 돕니다.

사용 사례 — 모델이 판단해서 하는 정리

메일을 읽어라. 릴리즈 담당자에게서 온 것이 있으면 /tidy-context 를 실행해라.
  • 두 층 — 스위치는 여부, 목록은 무엇이고 따로 적어둡니다. 그래서 스위치를 꺼도 선택해둔 것이 사라지지 않습니다.
  • 내장 명령 — model_commands에 슬래시를 붙여 이름을 적습니다.
  • 커스텀 명령과 스킬 — 각자의 frontmatter에 model_invocable: true로 스스로 참여합니다.
  • 와일드카드 없음 — 적으면 /permission-skip-all까지 들어가는 목록이므로, 파일에 이름을 적는 행위여야 합니다.
  • 셸 스플라이스 제외 — 백틱 셸 스플라이스를 포함한 명령은 절대 model-invocable이 될 수 없고, 그 거절은 조용히가 아니라 이름을 대며 이루어집니다.
켜기 전에 읽을 것

모델은 자기가 읽은 것으로부터 명령을 실행할 시점을 판단합니다. 파일, 명령 출력, MCP 서버가 반환한 무엇이든 포함됩니다. 즉 목록에 있는 것은 모델이 쓰지 않은 텍스트로부터 도달 가능합니다. 스위치도, 목록도, 설정 창의 안내도 모두 그렇게 말합니다.

사용 사례 — 실행 중인 세션을 다른 사람에게 보여주기

데몬이 HTTP로 화면을 제공하므로, 그 주소에 닿을 수 있는 다른 사람이 같은 세션을 그대로 엽니다. 같은 대화 내용, 같은 실행 중인 도구, 같은 권한 확인 창이 실시간으로 갱신됩니다. 내보내기도, 사본도 없습니다.

# localcode를 돌리는 머신에서
localcode --headless --listen 127.0.0.1:4096

# 상대방 머신에서
ssh -L 4096:127.0.0.1:4096 you@your-machine
# 그다음 http://127.0.0.1:4096 열기

같은 주소에 터미널을 하나 더 붙일 수도 있습니다. localcode --server http://127.0.0.1:4096은 누군가 브라우저로 보고 있는 세션에 TUI를 붙입니다.

인증 토큰이 없습니다

listen 주소에 닿을 수 있는 사람은 셸 실행을 포함한 API 전체를 얻습니다. 위처럼 loopback에 바인딩하고 SSH 터널로 공유하십시오. 신뢰할 수 없는 네트워크에서 0.0.0.0에 바인딩하지 마십시오.

11. 프롬프트 창

자동완성과 턴 이동

명령 자동완성

이름 일부를 치고 오른쪽 방향키를 누릅니다. 스킬, 커스텀 명령, 데몬의 명령, 각 클라이언트 자체 명령이 모두 한 목록에 있습니다. 전부 같은 방식으로 실행되고, /sm을 치는 사람은 그 이름이 어느 목록에 있는지 생각하고 있지 않기 때문입니다.

  • 추측이 아니라 순회 — 누를 때마다 다음 후보를 제시하고, 마지막 정거장은 처음 친 그 텍스트입니다. 빠져나올 수 없는 순환이 되지 않습니다. 여기서 최장 공통 접두사로 완성하는 방식은 쓸모가 없습니다. 스킬은 하는 일로 이름이 붙어서 pdf-tools와 pptx의 공통 접두사는 한 글자입니다.
  • 문장 중간 — 명령 이름은 창 맨 앞이 아니라 쓰인 자리에서 완성됩니다. read the mail, then run /tid가 완성되고 양쪽 문장은 그대로 남습니다.
  • 경로는 건드리지 않음 — 단어를 여는 슬래시가 아니면 명령이 아닙니다. internal/tui/co와 /Users/me/co는 무시됩니다.
  • 대화 이름도 — 같은 키가 #<이름> 참조를 문장 안에 끼워 넣으며 완성합니다.
  • 양쪽 클라이언트 — 같은 키, 같은 목록, 같은 개수 표시줄.

내가 보낸 턴 사이를 이동하기

사용 사례 — 마흔 턴 전에 내가 뭘 물었는지 찾기

  • Alt+↑와 Alt+↓는 화면을 내가 보낸 턴에서 다음 턴으로 옮깁니다. 사이에 모델이 쓴 것은 전부 건너뜁니다. 턴이 쉰 개인 세션에서 프롬프트를 찾는 방법입니다. 브라우저 화면 전용이고, 터미널은 같은 턴 표시는 그리지만 이 키는 연결하지 않았습니다.
  • ↑와 ↓는 별개이고 텍스트를 옮깁니다. 이전 프롬프트를 대화별로 창에 불러옵니다. 세션을 열 때 대화 내용에서 목록을 다시 채우므로, 대화를 다시 열면 예전에 무엇을 물었는지 그대로 불러올 수 있습니다.
  • 왜 둘인가 — 내가 물었던 것을 되읽는 일과 고쳐서 다시 묻는 일은 다른 작업이고, 키 하나가 둘 다 하려면 다른 하나를 빼앗아야 합니다.

위로 스크롤하면 모델이 아래에 아무리 써도 화면은 그 자리에 머뭅니다. 양쪽 클라이언트에서, 그리고 백그라운드 작업 자체의 창에서도 그렇습니다. 맨 아래로 다시 스크롤하면 최신 출력 따라가기가 재개됩니다.

12. 길어진 대화 목록을 쓸 만하게 유지하기

이름 변경, 순서 변경, 보관, 복원

동작하는 일사용 가능한 곳
이름 변경자동 생성된 id 대신 내가 지은 제목을 붙입니다. #<이름>이 해석하는 대상이 바로 이 제목이므로, 이름을 바꾸는 것은 그 대화를 다른 대화에서 인용할 만하게 만드는 일이기도 합니다.브라우저, 데스크톱 창
순서 변경카드를 드래그해서 위아래로 옮깁니다. 순서는 데몬에 저장되므로 모든 클라이언트에서, 재시작 후에도 같은 순서입니다.브라우저, 데스크톱 창
보관 (archive)조용해진 대화를 목록에서 내립니다. 이벤트 로그를 포함해 갖고 있던 것은 전부 유지합니다.양쪽 클라이언트 (/archive)

사용 사례 — 끝냈지만 버리지는 않은 대화

  • 여전히 읽힘 — 보관된 대화는 삭제된 대화가 아닙니다. 그게 보관하는 이유입니다.
  • 여전히 기록됨 — 보관보다 오래 사는 백그라운드 작업은 자기가 끝났다는 사실을 여전히 기록합니다.
  • 여전히 참조됨 — #<이름>이 보관함까지 찾습니다. 지난달에 치워둔 대화가 바로 지금 인용하고 싶은 그 대화입니다.
  • 거절하는 것 — 새 작업을 시작하는 것입니다. 위임, 백그라운드 작업, 예약 실행. 저장소 수준의 불변식 하나가 셋을 동시에 막습니다. 호출 지점마다 검사를 두는 방식이 아닙니다.
  • 강제하지 않음 — 턴이나 백그라운드 작업이나 예약 실행이 도는 중에는 보관이 거절됩니다. 삭제는 기록이 사라지므로 그 작업을 죽이지만, 보관에는 그런 명분이 없습니다.

13. 프로젝트를 벗어나는 경로

workspace 경계

세션 자신의 workspace를 벗어나는 경로는 그 자체로 별개의 질문이며, 도구를 써도 되는지와 다릅니다. "이 에이전트가 파일을 읽어도 된다"에 예라고 답한 것이 "~/.ssh를 읽어도 된다"에 답한 것은 아닙니다.

경우처리
절대 경로, 또는 ..이 든 경로해석한 뒤 세션의 workspace와 대조해 판정
workspace 안에 있지만 ~/.aws를 가리키는 심볼릭 링크바깥으로 판정. 물리 경로로 판단하므로 링크가 목적지를 세탁하지 못함
이제 막 생성될 파일존재하기 전에, 그 링크가 어디로 이어지는지로 판정
아예 해석할 수 없는 경로맹목적 허용 하나가 아니라 질문 하나를 치름
자격증명 파일: .env, *.pem, id_rsa, ~/.ssh, ~/.aws/credentials, .netrcSmart Agent가 켜져 있으면 즉시 거절. deny 등급이라 어떤 skip으로도 열리지 않음
workspace를 벗어나는 셸 명령이 두 스위치의 적용 대상이 아니고, 대화상자가 그렇게 밝힘. 셸 명령은 경로가 아니며 bash는 자기 기준으로 따로 물음

사용 사례 — 프로젝트 하나, 경계 하나, 세션 여럿

  • 세션 단위 — 경계는 묻고 있는 그 세션의 workspace입니다. 데몬 하나 위의 두 프로젝트에 있는 두 대화가 각자의 경계를 갖습니다.
  • 적용 대상 — 읽기는 read_file, grep, glob. 쓰기는 write_file, edit.
  • 고를 수 있는 답 — 이번만 허용, 이 세션 동안 허용, 이 디렉터리 허용, 또는 바깥 전반 허용. 기억된 것은 /read-outside mem-clear로 다시 잊게 할 수 있습니다.
  • 터미널에서 — /read-outside와 /write-outside가 같은 두 스위치를 조작합니다. /permission-skip-tools는 의도적으로 도구 확인만 건너뛰고 프로젝트를 벗어나는 경로는 계속 묻습니다.

그 밖의 차이

영역다른 점
검색 결과200개 상한, 64KB를 넘는 줄, 읽지 못한 파일을 각각 출력에 명시합니다. 개수가 아니라 경로를, 최대 세 개까지. 한 파일이 grep 결과 200개 중 30개를 넘게 차지할 수 없습니다.
라이프사이클 훅도구 훅 외에 pre_model(요청 차단, 또는 모델이 찾을 수 없는 사실 주입), post_model, delegate(서브 에이전트 거절. 프롬프트로는 못 하는 일), compact, retry.
세션별 workspace데몬 하나에서 두 프로젝트의 두 세션. 자기 세션의 턴만 자기 전환을 막습니다.
Effortoff, low, medium, high를 프로파일별 또는 대화별로. 설정하지 않으면 아무것도 보내지 않으므로, 손대지 않은 환경의 요청은 바이트까지 그대로입니다.
진행 중 지시턴이 도는 동안 입력한 메시지가 모델의 다음 도구 호출 지점에서 그 턴에 전달됩니다. 입력한 순서대로입니다.
거의 맞는 도구 이름장식이 붙었지만 그 에이전트가 실제로 가진 도구 하나를 명확히 가리키는 이름은 실행하고 어느 철자가 맞았는지 알려줍니다. 해석은 그 에이전트에게 제공된 도구 안에서만 이루어지므로, 오타가 tools 제한을 넘어설 수 없습니다.
모델별 습성모델 id를 기준으로만 적용하고 다른 어디에도 적용하지 않습니다. 작업 중간에 멈추는 muse 계열에는 계속하라는 신호를, Gemma에는 LaTeX 벗기기를.
환경변수 설정config.json의 모든 문자열이 {env:NAME} 또는 {env:NAME:-fallback}일 수 있습니다. 없는 변수는 그 변수와 요구한 필드를 지목하는 오류이지, 나중에 401로 실패하는 빈 문자열이 아닙니다.
이벤트 전달뒤처진 클라이언트는 조용히 건너뛰어지지 않고 그 사실을 통보받습니다. 스트림이 끝나고, 다시 연결해, 놓친 부분을 세션 로그에서 재생합니다. 빠짐도 중복도 없습니다.
Linux 설치root 없이. 정적 바이너리를 ~/.local/bin에 두고 $HOME 밖에는 아무것도 쓰지 않습니다. root를 쓸 수 있으면 .deb와 이식 가능한 tarball도 있습니다.

같은 점

다음은 의도적으로 다른 도구들과 같게 둔 것입니다. 위의 표들이 기능 개수 자랑이 아니라 차이로 읽히려면 이 목록이 있어야 합니다.

  • 되돌리기와 비우기 — /rewind와 /clear는 의도적으로 Claude Code의 범위를 따릅니다.
  • 프로젝트 컨텍스트 — @path 임포트가 되는 AGENTS.md와 CLAUDE.md 폴백. ~/.claude/CLAUDE.md도 적용되므로 기존 설정을 대체하지 않고 재사용합니다.
  • MCP — 세 가지 전송 방식 모두, 그리고 localcode mcp import-claude가 기존 Claude Code 설정을 가져옵니다.
  • 스킬과 커스텀 명령 — 같은 디렉터리 규약과 같은 점진적 공개 방식.
  • 도구 훅 — pre_tool_use, post_tool_use, user_prompt_submit, stop, session_start.
  • 권한 — 이번만 허용, 세션 동안 허용, 항상 허용. 마지막 것은 config.json에 기록됩니다.
  • 압축 — 요청 시, 그리고 임계값을 넘으면 자동으로.
  • 프롬프트 히스토리 — 프롬프트 창의 ↑와 ↓. 여느 셸과 같습니다.

전제와 한계

  • 비교 표의 오른쪽 열은 일반적 기준선입니다. 2026-09-01 기준으로 널리 쓰이는 코딩 에이전트들의 공통 모습을 서술한 것이지, 특정 제품에 대한 기능 감사가 아닙니다. 이 도구들은 자주 출시되므로, 없다고 적힌 기능이 이 글을 읽는 시점에는 있을 수 있습니다.
  • 2부가 전부 유일한 것은 아닙니다. 하나의 라이브 세션을 여러 화면이 공유하는 것과, 내가 보낸 턴 사이를 이동하는 것은 드뭅니다. 이름 변경·순서 변경·fork는 여러 도구가 어떤 형태로든 갖고 있는 편의 기능이며, 이 문서가 localcode를 쓰는 경험에 대한 것이기도 해서 실었습니다.
  • localcode에 대한 모든 서술은 v0.84.0에 실제로 들어 있는 동작입니다. USAGE.md에 문서화되어 있고 저장소의 테스트 게이트가 검증합니다.
  • 벤치마크 수치는 25개 인스턴스 한 번의 실행이고 에이전트 간 격차는 실행 간 편차 안에 있습니다. 그 실행이 무엇을 뒷받침하고 무엇을 뒷받침하지 않는지는 벤치마크 문서를 보십시오.
  • 두 기능은 제품에서 실험적이라고 표시되어 있습니다. 네이티브 데스크톱 창, 그리고 적용은 되지만 localcode를 재시작하지는 못하는 Windows 자체 업데이트입니다.
