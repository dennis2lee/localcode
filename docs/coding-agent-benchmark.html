Does the coding agent matter, or only the model?

Claude Code, opencode and localcode were given the same 25 SWE-bench Verified issues, the same model, the same budget and the same open permissions. Only the agent around the model differed.

Where all three failed the same way

Only one instance defeated every agent: django__django-12193. It reads as a rendering bug in Django's SplitArrayWidget, but the cause is CheckboxInput.get_context mutating the attrs dictionary it is handed. All three agents patched the call site instead:

- self.widget.get_context(name + '_%s' % i, widget_value, final_attrs)
+ self.widget.get_context(name + '_%s' % i, widget_value, final_attrs.copy())

That removes the symptom the issue describes and leaves the cause. The hidden test exercises CheckboxInput directly, so none of them passed it. Three different harnesses making the same mistake at the same layer is evidence about the model, not about the agents around it — which is the sharpest thing a fixed-model comparison can show.

How it was measured

Two phases, deliberately separate. In phase A each agent works inside that instance's own official SWE-bench evaluation image, so the repository's test environment is already installed; only the resulting git diff is kept. In phase B the official SWE-bench harness applies the dataset's own test_patch before running anything, then runs the FAIL_TO_PASS and PASS_TO_PASS sets. An agent that edits tests to make them pass gains nothing, because its edits are overwritten. That property is the reason scoring is not something the agent container reports about itself.

What is held equal:

  • One model id for all three, over the Anthropic API directly — no proxy in front of any agent.
  • A fresh HOME per run, so no host config, plugin, hook or prior memory reaches any agent. How that is done.
  • The same unprivileged user for all three. Claude Code refuses to bypass permissions as root, so rather than special-case one agent, none of them run as root.
  • The same prompt, the same 30-minute budget, and permissions fully open. An agent that stopped to ask would otherwise score zero for being careful.
  • Delegation off in all three. Claude Code's subagents, localcode's Smart Agent and Orchestrate: none were enabled, so this measures the single-agent path each ships with.

How “a fresh HOME” is actually made

Three of these tools keep state in the home directory — credentials, plugins, hooks, custom commands, a memory index, a session list. Any of it leaking in would mean measuring the machine rather than the agent, and it would not leak in evenly: the laptop this ran on had an opencode config with a local-model provider and a plugin in it, and a Claude Code install signed in to a subscription.

So the home directory is built from nothing for every single run, inside the container, before the agent starts:

AGENT_HOME=/tmp/agenthome
rm -rf "$AGENT_HOME"; mkdir -p "$AGENT_HOME/.config/opencode"
cp /bench/opencode.json "$AGENT_HOME/.config/opencode/opencode.json"
chown -R "$BENCH_USER" "$AGENT_HOME" "$REPO" "$OUT"

setpriv --reuid=... --regid=... --init-groups \
    env HOME="$AGENT_HOME" PATH=/agents/node/bin:... \
        ANTHROPIC_API_KEY="$ANTHROPIC_API_KEY" \
    python /bench/runagent.py --out "$OUT" -- "$@"

Four things make it hold. The container is started with --rm from the instance's stock image, so nothing survives a run or arrives from the previous one. The host's own home is never mounted — the only bind mounts are the read-only agent toolchain, the read-only prompt and config directory, and the output directory. HOME is set in the environment handed to the agent process itself rather than inherited, so a tool that looks up the home directory from the passwd entry and one that reads $HOME both land in the same empty place. And the API key arrives as an environment variable rather than a credentials file, which is what lets the home directory stay empty at all.

Exactly one file is placed there on purpose: opencode's permission rule, because its equivalent for the other two is a command-line flag. localcode's configuration is passed with --config and Claude Code's with flags, so neither writes to the home directory before it starts. Everything else those tools create there, they create themselves, from empty, every time.

Where the tasks and the scoring come from

Nothing here is home-made except the runner. The task set, the environments and the scoring are all the published SWE-bench artefacts:

  • Tasks: SWE-bench/SWE-bench_Verified on Hugging Face — 500 instances, each carrying the issue text, the base commit, the reference patch and the two test sets.
  • Environments: the official per-instance evaluation images published on Docker Hub as swebench/sweb.eval.x86_64.<instance>, so each repository's test suite is installed exactly as the benchmark authors built it.
  • Scoring: the SWE-bench harness, version 5.0.2, run unmodified.
  • What “Verified” means: the 500 instances human-screened as solvable and correctly specified, out of SWE-bench's original 2,294.

How these 25 were chosen

Selection is where bias enters a benchmark this small, so the rule was fixed in code before any agent ran and is deterministic — re-running the selector reproduces the same 25 instances. They were drawn in two batches from the 500 in SWE-bench Verified.

The first five were a pilot, one instance from each of five repositories, taking the instance with the median problem-statement length in its difficulty bucket — median rather than shortest, so the pilot was not quietly made easy.

The other twenty excluded those five and were drawn round-robin across repositories, one per repository per pass, ordered within each repository by a hash of the instance id. Round-robin because the obvious alternative — sorting and taking the first N — silently returns an alphabetical sample: an early version of this selector produced twenty instances that contained no sympy, no sphinx and no scikit-learn at all. Their difficulty quota was fixed in advance at 6 under 15 minutes, 10 15 minutes to an hour, 4 one to four hours; together with the pilot the 25 come out as 8 under 15 minutes, 13 15 minutes to an hour, 4 one to four hours.

Two consequences worth stating plainly. Django is 46% of SWE-bench Verified but only 3 of these 25, because the round-robin caps any one repository; the sample spans all 12 projects instead. And the quota over-represents the harder buckets against the dataset's own mix (39% / 52% / 8% / 1%), deliberately: the pilot put all three agents on 4 of 5, which separates nobody. Both choices make these rates incomparable to published leaderboard numbers — they are a comparison between the three agents on one fixed sample, and nothing more.

What the harness had to fix first

Most of the work was not running the benchmark but establishing that it measured anything. Four faults produced plausible-looking numbers that were wrong, and each would have been reported as agent quality:

  • opencode was never given the chance to work. Its own permission layer denied every FileSystem.writeFile, and --auto does not cover that. It spent whole budgets searching the filesystem for what was blocking it — find / ... grep -l "blocklist\|denylist" — and once tried to delete the file it could not edit. It needed a permission rule in config, which is what the other two got as command-line flags.
  • opencode does not exit. Inside the eval images it prints its final message and hangs, where the same command exits in three seconds on the host. Charging it the full timeout would have reported a run it finished in a minute as a 30-minute failure. The harness now stops it on its own completion marker and records which of exit, marker or timeout ended every run.
  • localcode died on every multi-turn conversation. Sonnet 5 returns thinking blocks with empty text by default; localcode's omitempty tag dropped the field on replay and the API rejected the request. Fixed upstream in v0.79.2 with a dedicated marshaller for thinking blocks.
  • The scorer silently compared against the wrong task list. Its --tasks default pointed at the pilot file, so scoring the 20-instance run without naming its task file produced a clean 0 resolved for all three — indistinguishable from three agents that solved nothing. It now refuses when a predictions file holds instances the task list does not.

A benchmark that cannot tell its own bugs from its subject's is not measuring the subject. Every one of these was found by reading what the agents actually emitted, not by looking at the scores.

What opencode's stall actually looked like

Worth describing precisely, because “timed out” suggests an agent that worked for thirty minutes and did not finish, and that is not what happened. Reading the event stream of a stalled run:

  • It started normally and did real work — between three and seven tool calls, reading files and grepping the repository.
  • The timestamps on those events span 10 to 22 seconds. Then the stream stops.
  • Nothing is emitted for the remaining ~1,780 seconds, until the budget expires and the process is killed.
  • The last event in every case is a step_finish following a tool call that completed successfully. The tool ran, the step closed, and the next model request never produced anything.
  • stderr is empty. No exception, no rate-limit message, no reconnect attempt. It simply stops.

There is a second, milder version of the same behaviour that shows up on runs that succeed: opencode prints its final answer, emits its terminating event, and then does not exit. On the host the identical command returns in about three seconds. Left alone it would be charged the full budget for work it had finished in a minute, which is why the harness stops it on its own completion marker and records whether each run ended by exiting, by that marker, or by the timeout.

Both point the same way: something in the process does not come back after a step boundary in this environment — an emulated x86-64 Linux container under Rosetta — sometimes at the end of the turn and sometimes in the middle of one. Running the cells one at a time recovered two of the five, so contention is part of it but not all of it: three stalled again with nothing else on the machine. Whether the cause is opencode, its Bun runtime, or the emulation is not something this benchmark can settle, and the figure above is reported as a floor for exactly that reason.

What this does not establish

Twenty-five instances at one run each. These agents are stochastic: the same agent on the same instance does not always produce the same patch, and this design cannot measure that spread. A three-instance gap between the best and the rest is suggestive and is not significance. Separating “better” from “luckier” needs repeats — at least three per instance — which the harness supports and this run did not use.

The instances were also weighted harder than SWE-bench Verified's own mix, so these rates are not comparable to published leaderboard numbers.

Does delegation earn its cost?

The same 25 instances, twice, on localcode v0.80.1: once with Smart Agent and Orchestrate off, once with both on. The two configurations differ in delegation and nothing else — same binary, same localcode run command, same model, same reply cap, same effort, same permissions.

DelegationResolvedAvg secAvg tool callsAvg output tokens
off19 / 2516729.89,434
on21 / 2513929.57,586

Delegation is ahead by two instances and finished faster while making the same number of tool calls, which is the shape you would expect if sub-agents are absorbing the wide reading. But the two arms do not merely differ by two: they disagree on five instances, in both directions. Delegation won seaborn-3187, requests-2931, pytest-10356 and sphinx-8056; it lost scikit-learn-25747 and sympy-13798. A net of two out of five disagreements is not a result at this sample size.

The control moved more than the treatment did.

Plain localcode scored 22 of 25 earlier on this same instance set, and 19 here. Nothing about the agent changed except its version and two profile settings. If one configuration of localcode can differ from another configuration of localcode by three instances, a two-instance gap between delegation on and off carries no weight. Establishing whether delegation helps needs repeated runs per instance, which this does not have.

One thing the run does establish is an accounting gap: with Smart Agent on, localcode's usage events report input_tokens: 2 instead of the context each call was sent, so the delegating arm cannot be compared on input tokens at all. The totals are left blank rather than summed, because a two-digit total would have read as delegation being extraordinarily frugal.

Until v0.80.0 the question could not be asked through the CLI at all: the switches could be set but the one-shot run registered no Task tool, so a model told to delegate went looking for a tool it had not been given. Both arms now run through the same localcode run command, and the two configs are written to differ in delegation and nothing else — same version, same reply cap, same effort, same permissions.
