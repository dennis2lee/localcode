# Changelog

## v0.49.0

* **Every document in the repository re-read against the code, and the stale parts fixed.** The ones that mattered: `MODELS.md` said the newest Claude models "cannot be used through Bedrock", which is now two integrations and a disagreement between Anthropic's and AWS's own documentation rather than a flat no, and its 1M-context advice was written before Opus 4.6 and Sonnet 4.6 had a 1M window there at all; `USAGE.md` said a session's workspace is "never rewritten" (it moves with the session, since v0.39.0) and that a slash command typed mid-turn is silently ignored (both clients have refused it out loud since v0.37.0); `INSTALL.md` asked for Go 1.23 (go.mod says 1.26.5), showed `make dist` without the `VERSION`/`GUI_EXE` it now requires, and said every MCP server is launched over stdio; `README.md` pointed at an `app.js` that has not existed since the Web UI became ES modules. `RELEASING.md` now lists every asset a release publishes, because the update check reads that list and a missing one reads as "nothing for your platform". The August 2026 code review's M18 is marked fixed (v0.42.0 fixed it sideways) and M19 re-checked as still open and moved into IMPROVEMENTS; the refactoring plan says up front that it finished in v0.31.0, so nobody reads it as work outstanding. USAGE's config table now lists every key the `Config` struct actually has — checked by a script, not by eye.

* **Linux packages: a `.deb` for Ubuntu and Debian, and a portable tarball.** Reported as "Ubuntu 24 needs an install too". `sudo apt install ./localcode-x.y.z-linux-amd64.deb` puts the binary in `/usr/bin` for every user and upgrades in place; amd64 and arm64 both ship, and a tarball with the same static binary covers every other distribution. There is no `Depends:` line because there is nothing to depend on — Linux builds are `CGO_ENABLED=0`, so one file runs on any glibc or musl. The update check knows the difference between the two: a copy dpkg installed is offered the `.deb` with the `apt install` line to run, and a copy someone unpacked is offered the tarball, because handing over the wrong one leaves two localcodes on the machine and no way to tell which is running. Nothing is installed for you there: that needs root, and localcode does not ask for a password or drive a package manager on your behalf. There is no desktop window on Linux — it links a webview through CGo — so a Linux install is the daemon, the TUI, and the Web UI in a browser. The package is written by localcode itself (`internal/debpkg`, about two hundred lines over `archive/tar`), not by `dpkg-deb`, because releases are cut from a Mac and that tool is not on one; its tests read the package back out and assert the structure dpkg requires, and hand it to `dpkg-deb` itself wherever one exists.

## v0.48.0

* **A model that stops mid-task can be told to carry on, without you typing it.** Reported with the transcript: a build fails, the model reads the error, writes "`global_init.cpp` also has to be updated" — and ends its turn. "진행" makes it finish that step, and it stops again one step later. v0.46.0 fixed the mechanical half of this, where the reply *did* ask for tools and the turn was ended anyway because the server had labelled the stop reason "stop"; what was left is a model that genuinely stops, with nothing in the reply to run and nothing to tell it apart from one that has finished. Two things now: the models this has been reported against are told, in the system prompt, to take the next step in the same turn instead of describing it; and `keep_going` is localcode typing "carry on" for you, at most N times per turn. Models known to stall get a budget of 3 out of the box, so installing the release is the whole fix; for everything else it stays off — a turn that ends after tool use looks identical whether the model finished or gave up, so on a model that stops when it is done this would cost a turn per task. A profile's own `keep_going` overrides either way, and `-1` means never. The carry-on itself is persisted as the user message it is (marked so no client paints it as something you typed), because a version that kept it only in memory rebuilt a restarted session's history with two assistant messages back to back — a shape Bedrock rejects outright. It is not applied when nothing ran in the turn, when the last tool call was refused, when the reply ends in a question, when the reply hit `max_tokens`, when you have already typed something that has not reached the model yet, or when the previous carry-on produced no work — that last one is what makes a finished task cost one extra turn rather than the whole budget. Every carry-on is a note in the transcript, so a turn that continues by itself never looks like one that never stopped.

* **A speech server that can stream is now used as one, over a WebSocket.** Whisper reads a window of audio at a time, so showing text mid-sentence meant re-sending the whole utterance every 900ms and discarding the previous answer — wasted work by construction, and over a network wasted upload too: ten seconds into a sentence, every preview shipped those ten seconds again. Where the server at `whisper_url` speaks [WhisperLive](https://github.com/collabora/WhisperLive), the audio now goes out once as it is recorded and the text comes back as the server produces it, so the grey text keeps up with the words instead of trailing them by up to a second, and the cost of a sentence stops growing with its length. It is tried first whenever `whisper_url` is set and `whisper_api` is empty; a server without it answers the upgrade with an ordinary HTTP status, which costs one request and falls back to the upload dialects unchanged. `whisper_api: whisperlive` pins it, and then a server that does not answer is reported rather than quietly downgraded. `localcode dictation probe` asks about the streaming endpoint too. The pause that turns grey text into committed text is still decided here from the audio, so dictation behaves the same way whichever kind of server is at the other end — including the wait for the last words of a sentence, which are still in flight at the moment a speaker stops. No new dependency: the WebSocket client is about 300 lines in `internal/dictation/websocket.go`.

## v0.47.0

* **The Send button switches dictation off, as Enter always has.** Sending finishes the sentence by definition, so the microphone goes off with it and the words still being transcribed go into the prompt rather than into the box behind it. Enter did this; the button was wired straight to "send" and left dictation running — a split invisible in use until you happen to click rather than press. Both controls now go through one path.

* **Fix: the workspace at the top did not always follow the session.** Opening a conversation POSTed that session's own directory back to the daemon purely to update the label. The workspace has been per-session since v0.39, so the request moved nothing — but the daemon refuses a workspace change while that session has a turn in flight, which is the ordinary state of a session you left working and came back to. The refusal left the header naming the *previous* session's project and printed an error about a move nobody had asked for. It now reads the directory instead of writing it, paints it from the listing immediately and confirms against the daemon, and drops an answer that arrives after you have switched again.

* **The microphone list can be filled in without dictating first.** A browser hides the device list until it has been allowed to use the microphone once — and several report one anonymous input and nothing else, so a headset or USB microphone plugged in since then was missing from the settings panel entirely and appeared only after dictating, which is backwards: the panel is where you pick the microphone you are about to use. There is now a button that asks for access and lists them, and a device plugged in or unplugged while the panel is open lands in the list on its own. Opening the panel still asks for nothing.

* **The spoken language takes effect when you choose it.** Reported as "I said *I'm a boy* in English and it wrote 아이엠어보이". The panel's Close button discarded the choice without a word, so picking English and closing left the daemon still set to Korean — and forcing a language the audio is not in does not make whisper transcribe *worse*, it makes it write the audio **in that language**: Korean audio with English selected comes back as an English translation, and English audio with Korean selected comes back spelled out in Hangul. The dropdown is a finished decision the moment it changes, so it is applied then, carrying the engine address the daemon last confirmed rather than whatever is half-typed in the boxes. The address keeps its Save button — it cannot be applied as it is typed — and editing it now says out loud that what is on screen is not yet in force.

* **The spoken language says when the engine cannot honour it.** Reported as "I said *I'm a boy* in English and it wrote 아이엠어보이" — which is not a mis-transcription but a Korean-only model doing the only thing it can with English audio, spelling it out in Hangul. The sherpa engine is one model per language and the model `dictation install` fetches is Korean, so the Spoken language control does nothing at all for it while appearing to be in force. The settings panel now says so beside the control, with the way out (install whisper, which is multilingual and is preferred wherever it is installed), and `localcode dictation status` prints the language in force and the same note. Whisper takes the language per request and says nothing, because a warning that is always there is not read.

* **`dictation install` no longer stops with nothing done where there is no prebuilt engine.** localcode publishes a whisper build for Windows only, so on macOS and Linux install failed at the first step and downloaded nothing — including the model, which is the same file on every platform, is half the setup, and is the half a package manager cannot provide. The model is now fetched first and the engine step reports what remains. It also looks for an engine already on this machine and names it: `brew install whisper-cpp` ships `whisper-server`, and "build whisper.cpp yourself" is the wrong thing to say to someone who already has it. It is named, not adopted — pointing `dictation.whisper_bin` at a build localcode has not tested stays a choice you make, not one made quietly for you. The same sentence appears wherever "no speech engine installed" is reported.

* **Fix: the spoken language was ignored by a WhisperX server.** That service reads its options from the query string and ignores form fields it does not know, so `language` — and the request for JSON output — went nowhere: every utterance was auto-detected whatever the settings panel said. They are now sent where it reads them, `task=transcribe` with them so a server configured to translate by default still transcribes, and "auto" is omitted rather than sent as if it were a language. The other two dialects took the language correctly and are unchanged.

* **Fix: a slow speech server was reported as one with no transcription endpoints.** The dialect search sent the *utterance* to each candidate in turn, sharing that sentence's deadline between them — so a server that takes a few seconds had the endpoint that would have worked cut off part-way through, and the transcript said `has none of the transcription endpoints localcode knows`. That sentence sends someone to reconfigure a server that was working. The search now runs against half a second of silence, which is cheap on any engine whatever its speed, and only then is the audio sent — to the one endpoint that answered. A candidate that never replies is reported as not replying rather than as absent, since those are different claims and only one of them is knowable.

* **An endpoint that refuses the request no longer hides one that works.** A WhisperX server offers an OpenAI-shaped endpoint *and* its own; if the first refuses permanently — a missing field, a model it does not have — the search used to settle there. It now keeps looking, and falls back to the refusal only when nothing else answers.

* **Fix: dictated sentences could arrive in the prompt box back to front.** Each sentence is transcribed by its own request and the requests overlap, so a short one overtakes a long one that started first — which happens on any engine slow enough to matter, meaning every engine on another machine. A sentence's place in the order is now claimed when the speaker stops, not when its text comes back, and a sentence still in flight holds back the ones behind it rather than letting them past.

* **Fix: switching the microphone off printed an error every time.** Stopping cancels the previews in flight — that is what makes the button feel immediate — and each cancellation was reported as a transcription failure, so a line of red appeared under a perfectly good transcript: `whisper engine: Post "http://…/inference": context canceled`. Cancelling our own work is not a failure. A deadline still is, and is still said.

## v0.46.0

* **The settings window can check for a new release and install it.** Two buttons under a new **Updates** heading, and neither does anything unasked: checking asks GitHub for the latest release of this repository and compares it against the running build, and installing downloads the file that matches how localcode was installed and starts the platform's installer. Nothing runs on a timer, and opening the panel checks nothing — a check is an outbound request that says which version this machine runs. The install button appears only in the desktop window, where the daemon and the person clicking share a machine; over `--server` it would replace the program on the *server* at a remote browser's request, so the check still works there and the install is refused with the release page instead. The download is verified against the SHA-256 GitHub records for the asset and refused if it does not match — a connection dropped at 90% otherwise produces an installer that opens, fails halfway, and leaves a broken install. On Windows the MSI is run through `msiexec /i`, which upgrades in place; on the platforms whose release is an archive, localcode says where the file is rather than unpacking it over the install that is running. See [USAGE.md](USAGE.md#checking-for-updates).

* **Fix: the last sentence of a remote dictation was thrown away, silently.** Reported three times as "no error and no text at all", and reproduced here at last by driving a whole session against a speech server that takes a second or two to answer — which is the only thing a remote engine ever is. Switching the microphone off cancels the engine work in flight, so that the click is not queued behind it; since v0.45.1 the work in flight is *the transcription of the sentence just spoken*, and Stop cancelled it and then waited three seconds for the transcription it had just cancelled. Against a local engine the sentence commits within a chunk or two and this never showed. Cancelling now means the previews only, which is what it was ever meant to mean; a finished sentence is left to arrive, and only closing the session — where there is nowhere left to deliver it — ends everything.
* **Fix: a dictation whose only failure was its last one said nothing about it.** Every reply to a chunk of audio carries the reason a transcription failed; the reply to *stopping* did not, so a failure in the final moments reached nobody. It carries it now, and the client shows it.
* **A failed final falls back to the preview of the same words.** A transcription that fails or runs out of time used to take the sentence with it. The last preview of that audio is imperfect and is what the person said, which beats an empty prompt box.
* **Longer to collect the last sentence: 8s, was 3s.** Three seconds was chosen against an engine on the same machine. Nothing waits on it — the microphone is already off and the prompt box is already usable — so the only thing it decides is whether the final words land in the box or are lost. The client's own limit was raised above the daemon's, since set below it, it gave up a moment before the answer arrived.

## v0.45.2

* **Fix: LaTeX font commands nested in each other were left on screen whole.** Reported with a screenshot of a Gemma reply: `$\mathbf{\text{ vs }}$` — the word "vs", wrapped twice — came through as itself, dollars, braces and both backslashes. The unwrapper took `\text{...}` and `\mathbf{...}` in a single pass, and a single pass can only reach the innermost pair of braces; the `\mathbf` it left behind then matched the test for "this is real maths, leave it alone", and the whole span was kept as source. It now strips them until nothing changes, and covers the rest of the family (`\boldsymbol`, `\mathcal`, `\texttt` and so on). Gemma's own note has been widened to name `\mathbf` and to ask for `**bold**` instead.

## v0.45.1

* **The request that delivers audio no longer waits for the speech engine.** This is the shape behind every remote-dictation failure so far. Committing a finished sentence was a blocking call *inside* the POST carrying the next chunk of audio, so the engine's time was time the browser sat on an open request, with the session's lock held and its own audio queueing behind it. On a local engine that is a few hundred milliseconds and invisible; on a server on another machine it is however long that machine takes, and every mechanism layered on top — the client's deadline, the lock, the queue — turned the delay into a failure, most recently as three rounds of `signal is aborted without reason`. The sentence is now transcribed on its own and delivered with a later chunk, a quarter of a second being the wait for one. Switching the microphone off still waits up to 3s for the sentence in progress and no longer.
* **Fix: a request the browser gave up on reported the browser's words for it.** `signal is aborted without reason` is what a fetch says when it is aborted, and the abort was rejecting the request before localcode's own explanation could — so the one message that reached the transcript named neither the engine, nor the deadline, nor anything to do about it. It now says which it was and points at `localcode dictation probe`.
* **More of Gemma's LaTeX is unwrapped.** `$S1 \sim S6$` — a range written as a formula — came through untouched, because `\sim` was not in the table. The table now covers the arrows, relations, set and logic symbols, Greek letters and spacing commands a model reaches for in ordinary prose. Anything left with a backslash in it is still shown as it was: that is real maths, and half-translating it would be worse than leaving the delimiters that say so.
* **Fix: the frameless Windows window could not be moved or resized.** Reported from the machine that has one: the caption was gone and the page's minimise/maximise/close worked, but dragging the bar did nothing and no edge would pull. The cause is that WebView2 renders the page into a *child* window covering the client area, so a press on the page is that child's message and the top-level window's `WM_NCHITTEST` is never consulted — v0.44.0's hit test was answering a question nobody asked. The buttons worked because they are ordinary page clicks, which is exactly what hid it. The page now reports the press instead: pressing the title strip or one of eight resize edges calls into the window, which releases the capture and hands Windows the same `WM_NCLBUTTONDOWN` its own frame would have, so moving, resizing, edge snapping and double-click-to-maximise all behave as usual. A test pins the command names the two halves share, since a name only one side knows is a control that silently does nothing.

## v0.45.0

* **Gemma's LaTeX renders as what it meant.** Gemma writes arrows and names as `$\rightarrow$` and `$\text{Bla-Bla}$` — correct in a chat client with MathJax in it, and literal dollars and backslashes in one without. Two halves: a model whose id contains `gemma` is now told, in its system prompt, that this window renders Markdown and nothing else and to write the character itself; and the renderer unwraps the ones that arrive anyway, so replies already in a transcript read properly too. Both are narrow — no other model is told anything, and a `$` span is only touched when it contains a LaTeX command, so `$PATH`, `$5` and real formulas are left exactly as they are. Other models with their own habits can be added to the same table in `internal/agent/quirks.go`.
* **Fix: dictation against a slow remote engine stopped itself.** Reported from the field, with the transcript to prove it: `the speech engine has not answered in 12s` alternating with `dictation stopped: read audio: http: request body too large`. Three faults, all fixed. The client's 12s deadline was *below* the daemon's own 25s cap on committing an utterance, so it aborted finals that were about to succeed; it is now a 60s backstop, and the daemon's own limits (20s for a preview, 45s for a commit) are what normally fire, with the reason instead of "no reply". Audio queued behind a slow request was concatenated into one body that outgrew the daemon's 256KB limit within seconds, which the daemon refused and the client counted as a failure — one request now carries at most 512KB, the rest stays queued in order, and the daemon's ceiling is 4MB. And a slow engine is no longer asked for a new preview the moment it answers the last one: the next one waits at least as long as the last one took, so the queue stops growing instead of growing forever.
* **Second attempt at removing the Windows title bar, and a log that says what happened.** v0.44.0's `WM_NCCALCSIZE` subclass left the caption on screen on the machine it was tried on. `WS_CAPTION` is now cleared from the window style as well (keeping the styles that carry resizing, the system menu and the minimise/maximise commands), so the caption cannot be drawn whichever mechanism Windows was ignoring. Because the desktop build has no console, and "the title bar is still there" looks exactly like "this build does not have the feature", it now writes `%LOCALAPPDATA%\localcode\gui-frame.log` on every launch: whether the subclass installed, the window style before and after, and whether the messages it depends on ever arrived.

## v0.44.0

* **The desktop window has no title bar on Windows either.** v0.43.0 did it on macOS, where the OS supports drawing the bar transparently over the window's own background. Windows has no such thing — the caption *is* the non-client area, and so are moving, resizing from an edge, double-click-to-maximise and the close button — so it is replaced rather than deleted: `WM_NCCALCSIZE` makes the client area the whole window, `WM_NCHITTEST` puts the resize edges back and makes a 28px strip across the top behave as the caption did (drag, double-click, right-click for the system menu), and the page draws its own minimise/maximise/close buttons in the part of that strip the hit test hands back to it. Alt+F4 and the taskbar's Close are untouched. **This could not be tried from the machine it was written on**, so `LOCALCODE_TITLEBAR=1` starts the window with the ordinary Windows frame if any of it misbehaves — see [USAGE.md](USAGE.md#desktop-window-experimental).

## v0.43.1

* **Fix: dictation against an unresponsive speech server hung, silently.** A server that accepts the connection and then never answers produced no text, no error, and a microphone pill that did nothing when clicked — stopping waited for the uploads to finish, and they never did, so dictation could only be switched off by reloading the page. Now: one chunk's upload is abandoned after 12s and says so in the transcript, three of those stop dictation with the reason, and clicking the pill switches the microphone off at once, waiting no more than 1.5s for already-recorded audio to flush. The daemon end matches — a transcription can now be cancelled, so a stop no longer queues behind a request that will never land, and a browser that gives up on a chunk takes that work with it instead of leaving the session's lock held. The per-transcription limits came down from 30s/60s to 12s/25s: against a local engine they never mattered, and against a remote one the timeout *is* the experience.
* **Fix: a speech server that hangs on one endpoint hid the one that worked.** The dialect search shared a single deadline, so the first candidate could spend all of it and the other two failed instantly on an expired context — every utterance, forever. Each candidate now gets its own share of the time.
* **A remote engine decodes the way the local one does.** Two of the options localcode passes to an engine it starts cannot reach a server someone else started, so they are handled from this side: every whisper.cpp-shaped request carries `temperature_inc=0.2` (whisper.cpp's own default), which overrides a remote server started with `--no-fallback` — the flag that drops exactly the segments fast speech produces — and timestamps are stripped from the answer in both shapes whisper emits them, so a server configured to include them cannot put them in the prompt box. `threads` stays the remote machine's own business.
* **The dialect search no longer runs for an engine localcode started itself.** It is whisper.cpp, because this is the code that spawned it. The comment had said so for a while; the code was still sending every local session's first utterance to `/v1/audio/transcriptions` to find out.

## v0.43.0

* **Fix: a turn with a local model stopped mid-task, and one more prompt carried on.** A reply that asks for tools is answered by running them; the reason the server gave for stopping is no longer the gate. Local servers do not agree on that reason — several report `finish_reason: "stop"` on a reply that carries tool calls, and some close the stream without sending one at all — and taking either at face value ended the turn with the calls sitting in the transcript unrun. From the outside the model announced what it was about to do and then stopped for no visible reason, and typing "carry on" made it pick up again. A tool call that arrives with no id (which the real API always sends and several local servers do not) now gets one rather than being silently dropped. A reply cut off by `max_tokens` is still the exception: it stops mid-write, so its last tool call has truncated arguments and is not run.
* **Every session box carries a light, grey when idle.** The left panel drew a dot only for a session that was working or had an unread reply, so a row with nothing on it could mean "idle" or "this panel does not draw lights". Grey and steady for idle, blinking green for a turn in progress, steady green for a reply that arrived while you were elsewhere.
* **Drag session boxes up and down the panel.** Newest-first is only a starting arrangement: it sinks the conversation you have lived in all week below every throwaway one started since. The order is saved on the daemon (`POST /api/sessions/order`, in each session's metadata file), so it survives a restart and is the same in every client. A session created after you arrange the panel still appears at the top.
* **The speech engine's address and port are two boxes in the settings window, and the engine's API is a dropdown.** A single address field invited "192.168.1.50" with no port and nothing to say one was wanted. `whisper_api` (`openai` / `whispercpp` / `whisperx`) is now settable and saved there too — discovery is right for almost everything, and cannot work against a server that answers every path. A remote engine is not a different feature: same grey-then-committed text, same pause detection, same errors, only a different machine doing the transcription.
* **Fix: dictation lost fast speech.** Two causes, both fixed. The 48kHz-to-16kHz conversion kept every third sample and discarded the rest, which does not remove the energy above 8kHz — it folds it back into the middle of the speech band as noise, and fast speech puts more energy up there (sibilants and plosives, closer together). It now low-passes before decimating, and handles a non-integer rate ratio such as a 44.1kHz device properly. Separately, the engine was started with `--no-fallback`, which drops any segment whose decode looks unconfident rather than retrying it — words running together is exactly what fails that check, so talking quickly could produce no text at all. Silence is still handled here: audio is only sent once the microphone has heard speech, and whisper's non-speech annotations are stripped from the reply.
* **`~/.claude/CLAUDE.md` is loaded, and project rules follow the session's workspace.** The global Claude Code file used to be a fallback reached only when `~/.localcode/AGENTS.md` did not exist, so anyone who had both silently lost one; both are read now. Project rules were worse off: they were read once at startup from the directory the daemon happened to be launched in, which for a desktop build opened from Finder or the Start Menu is not a project at all — so no `AGENTS.md`/`CLAUDE.md` was ever found, whatever workspace was open. They are now resolved per session from that session's own workspace and re-read each turn, so two sessions in two projects get their own rules and editing the file takes effect on the next message.
* **The desktop window has no title bar on macOS.** The bar is drawn transparent over the window's own background with the title hidden, so the app is one surface from the top down and the traffic lights float on it. The bar stays present, which is what keeps the window draggable and closable. Windows keeps its caption: removing it there means answering `WM_NCCALCSIZE` and `WM_NCHITTEST` by hand and drawing the buttons in the page, and that cannot be verified from the machine this was written on.

## v0.42.1

* **Prompt recall belongs to the conversation now, and survives leaving it.** Up/Down history lived in the per-session state a switch wipes, and nothing ever refilled it: opening another session and coming back left Up recalling nothing, and the prompts of the session you had been in were gone. Each session now keeps its own list, and it is also filled from the transcript the daemon replays when a session opens — so reopening a session, reloading the page, or attaching the TUI to an existing session recalls what was asked in it before, including prompts sent from another client. Still in memory only; the replayed transcript is the record. Capped at 200 entries per session.
* **Fix: the second Up in a row did nothing in the Web UI.** Recall parks the caret at the end of the text it inserts, and Up only recalled with the caret at offset 0, so history was one entry deep unless the caret was moved back by hand between presses. A walk already under way now continues wherever the caret is — the behavior the TUI has always had. Editing what was recalled ends the walk, so the next Up starts again from the newest entry instead of walking over an edit.

## v0.42.0

* **Fix: the light under the prompt could sit solid through a whole turn.** It read this client's own belief about whether it was waiting, while the light on the session's row in the left panel reads the daemon's busy flag — so anything that left the first false mid-turn showed one light blinking and the other steady about the same turn. A reload, a switch away and back, or a turn started from another client (the TUI, a second tab) all did it. Both lights now report the same thing, and the stop button is offered — and works — for any turn the daemon says is running, whoever started it.
* **Fix: a prompt did not appear until the model started work on it.** The user line was drawn only from the daemon's `message.user` event, which is written when the model is actually handed the text — after the hooks, the delegation decision and the first request. On a slow or remote model that is seconds of a screen that does not change, which reads as an Enter that never registered. The prompt is now echoed the instant it is submitted, dimmed, and the daemon's own line replaces it when it arrives: one entry per message, and a reloaded session still shows exactly what the live one did. Same in the TUI and the Web UI/desktop window.
* **Fix: the folder button beside the workspace opened nothing on Windows.** Two causes, both invisible from macOS. The window was being started hidden — the helper that keeps console children from flashing a black box also sets `SW_HIDE`, and Windows applies that to the first window a GUI child creates, which for `explorer.exe` is the folder window itself. And a workspace path written with forward slashes (`C:/Users/me/proj`), which every other part of localcode accepts, is silently ignored by Explorer, which opens the default Documents window instead. The path is now normalized to the OS's own form and made absolute first, and the three platforms have one implementation each: Explorer without the hide flag on Windows, Finder brought to the front (`activate`, the same fix the folder picker needed) on macOS, `xdg-open` elsewhere.

## v0.41.3

* **`dictation probe` discovers a WPAD proxy.** Windows has one proxy mechanism that leaves no URL anywhere localcode can read: "automatically detect settings", on by default, where the browser asks DNS for a host literally named `wpad` and fetches its `wpad.dat`. A machine can be proxying every browser request while the fixed proxy, the environment and `AutoConfigURL` are all empty — which is exactly the shape the reporting laptop turned out to have. When nothing else is configured, the probe now asks DNS the way the browser does, reads the script it finds, and tries the proxies named in it. An answer that is not a PAC script (a stray web server's error page on the `wpad` name) is ignored rather than mined for proxies.

## v0.41.2

* **`dictation probe` reads the proxy auto-config script and tries the proxies it names.** v0.41.1 read the registry's fixed proxy, and the machine that prompted all of this has none: like most corporate Windows setups it uses a PAC script (`AutoConfigURL`), which the browser evaluates per URL and which explains "the browser works and nothing else does" while the probe still said `proxy: none`. localcode cannot run the script — it is JavaScript — but it can pull the `PROXY host:port` entries out of it and try each one against the speech server. ## v0.41.1

* **Dictation traffic uses the Windows system proxy.** This is the answer to a contradiction the probe surfaced: an analysis made through a browser said the speech server answered `GET /` with JSON, and localcode's own probe said every byte sent — HTTP or TLS — had the connection reset. Both were true, about two different network paths. On a corporate laptop the browser goes through the IT-configured proxy in the Windows registry, which Go does not read; localcode connected directly, into whatever middlebox resets unproxied traffic. Dictation requests now use the `HTTP_PROXY`/`HTTPS_PROXY` environment when set (read fresh per request, not cached at startup, so exporting the variable after the fact works) and otherwise the same registry setting every browser on the machine uses, honouring `ProxyOverride`. Loopback is never proxied, whatever the registry says — the local whisper engine lives at `127.0.0.1`, and routing it to a corporate gateway would break local dictation on every proxied laptop at once.
* **`dictation probe` reports which proxy it is using** — environment, Windows settings, or none — because that is the invisible difference between the probe and the browser on the same machine. When everything is reset and no proxy is configured anywhere, the summary now says what that failure is and what to check.

## v0.41.0

* **Fix: an `https://` speech server address had its scheme thrown away.** `whisper_url` was normalized to a bare `host:port` and every request hardcoded `http://`, so an HTTPS server could not be reached at all — and the way that fails is the worst kind: a TLS port answers a plaintext request by closing the connection, with no status and no message. Identical, from this side, to a server refusing the request. https is carried through now.
* **`localcode dictation probe` identifies a port that speaks TLS.** When nothing gets through over plain HTTP it attempts a TLS handshake, and if that succeeds it says so and names the change to make. That turns the one failure with no evidence in it into a line of instruction. The certificate is not verified: the question is which protocol the port speaks, not whether to trust it, and refusing to answer over a self-signed certificate would withhold the fact being asked for.

## v0.40.2

* **New: `localcode dictation probe`.** It asks the configured remote speech server what it actually answers, one endpoint at a time, and prints every reply. This exists because the failure it diagnoses tells you nothing on its own: a server that resets the connection produces "an existing connection was forcibly closed by the remote host" with no status and no body, all three candidate endpoints then fail identically, and the transcript gets one line naming only the first. The probe asks the questions separately — does TCP connect, does a plain `GET` work, what does each upload endpoint say — and the distinction between the second and third is the one that matters: if `GET` works and every upload is reset, the address and the endpoint list are fine and something is dropping the audio itself, which is a different thing to go and look at.

## v0.40.1

Correcting v0.40.0's dictation fix, which had a bug of its own.

* **Fix: a connection reset settled the protocol search on the wrong endpoint.** v0.40.0 learned three server dialects and picked whichever answered, treating anything that was not a 404 or a 405 as an answer. A request that got no HTTP response at all — the server closing the connection mid-upload, which is what it does when it means to reject a request and does not wait to read the body — is not an answer, and it is not evidence about which endpoint exists. It settled the search anyway, so every later utterance went back to a path that was never going to reply, and the endpoint that does work went untried. A failure with no response now neither settles the choice nor ends the search.
* **Fix: an unreachable server was reported as one missing the endpoints.** Two different problems, and naming the wrong one sends you to look in the wrong place. It also leaves the dialect unsettled, so a network that dropped for a second does not disable dictation for the rest of the run.
* **Transcription requests now ask before sending the audio** (`Expect: 100-continue`). A server that means to reject the request answers as soon as it has the headers and closes the connection without draining the body, which arrives here as a connection reset with no status and no message. With this the rejection comes back as the status it really is.
* **New: the OpenAI `model` field is sent when `whisper_model` is set.** Some servers imitating that API require it. Sent only when configured, since a server hosting one model rejects a name it does not recognise.

## v0.40.0

* **Fix: dictation against a remote server could be completely silent.** localcode spawns whisper.cpp locally, so the only transcription endpoint it knew was whisper.cpp's — `POST /inference`, audio in a form field called `file`. Pointing `whisper_url` at another machine kept using exactly that, and a remote server is precisely where it is likely to be something else. The report was a WhisperX ASR server, which serves `/asr` and `/v1/audio/transcriptions` and answers `/inference` with 404: the microphone on, audio going out every 900ms, every request refused, and nothing on screen. Indistinguishable from a broken microphone. Three dialects are known now — OpenAI-compatible, whisper.cpp, WhisperX — differing in the path, the name of the file field, and which extra fields are accepted. The first utterance tries each and remembers which answered, so discovery costs two extra requests once per engine. Only a 404 or a 405 moves on; a 400 or a 422 is the endpoint existing and disliking the request, which is a real answer and must not become three confusing ones. `whisper_api` pins the choice. Replies are read for the words wherever they are (`text`, `transcription`, or a list of segments), since a transcript under a key nobody reads is indistinguishable from silence.
* **Fix: a failed transcription said nothing at all.** A failed partial was dropped because the next one is a second away covering the same audio; a failed final fell back to the last good partial because an imperfect transcript beats losing the sentence. Both are right on their own, and together they added up to dictation that could not fail out loud. The fallbacks stay — grey text is still not replaced mid-sentence — but the reason is now reported once, in the transcript.
* **The session light in the left panel says whether there is something to read.** Green rather than blue, matching the status light under the prompt, which has always been green for "connected and working". Blinking means the model is working; **steady** means it finished while you were somewhere else and the reply is waiting. Opening the session clears it. A turn that finishes in the session already on screen never sets it, since you watched the reply arrive. The steady state is what was missing: a turn finishing elsewhere used to just stop blinking, which is what the list shows for a session that has done nothing all day.

## v0.39.0

The workspace is per session now, and `os.Chdir` is gone.

* **New: each session has its own working directory.** It used to be the process's own — one `os.Chdir` for the whole daemon — and every awkward part of the workspace followed from that. A change had to be refused while a turn ran in *any* session, including one nobody was watching and one parked forever on an unanswered permission request, which is what "I often just can't change the workspace" was. Two clients on one daemon could not work in two projects, because selecting a session in one moved the other's ground. And reopening yesterday's session put its files wherever the daemon happened to be started today. Each turn now carries its session's directory on the context: `read_file`/`write_file`/`edit` join relative paths onto it, `glob` and `grep` search inside it, and `bash` runs in it. Nothing calls `os.Chdir`; the process's own directory is left where localcode was started and remains the fallback when nothing else is set, so every existing caller behaves as before.
* **A turn in another session no longer blocks a workspace switch.** This session's own turn still does: its tool call, mid-execution, would otherwise find the ground moved under it. That is a real race rather than an artifact of shared state, and it is one the person asking can see and wait out.
* **Searches answer in the terms they were asked in.** A relative pattern gets relative results, so a `grep` no longer prints the whole of `C:\work\localcode-main` in front of every line, and a path it reports can be handed straight back to `read_file`.
* **Changed: `POST /api/workspace` with an unknown session id is now 404,** where it used to answer 200. That was right when the directory was process-wide: it had already moved by the time the session was looked up, so failing would have reported a switch that did happen as an error. The session is what moves now, so there is nothing that succeeded. Omitting the session id sets the daemon's default — what a new session starts in — which is the only daemon-wide meaning the workspace still has.

## v0.38.0

Stop guessing what the server can take, and say so when a limit bites.

* **New: the context window is read from the server, not guessed from the model's name.** For a local server the name cannot answer the question even in principle: it serves whatever was loaded, under whatever name the file happened to have, and it is nearly always started with a *smaller* window than the model supports, because the window is what costs VRAM. A model capable of 128k routinely runs at 8k on a laptop, and that setup was being handed 128000 for the number that keeps every request inside the limit. `GET /v1/models` supplies it now, and `/props` for llama.cpp, which does not put it there. All five spellings the various servers use are read (`max_model_len`, `max_context_length`, `loaded_context_length`, `context_length`, `n_ctx`); where a server reports both a loaded size and the model's maximum, the loaded one wins, because that is what a request has to fit inside. An explicit `context_window` in config still wins over all of it, and anything that does not answer falls back to the name guess exactly as before. Asked once per provider and model, then remembered.
* **Fix: a reply cut off by `max_tokens` said nothing about it.** The providers report it, and it was dropped, so the text simply stopped, usually mid-sentence and often mid-function, with nothing to distinguish it from a model that had finished. The default cap is 4096, which makes this routine rather than exotic; unexplained, the reasonable conclusion is that the model is broken rather than that a number needs raising. The note names the limit that was actually applied and the profile to raise. Not reported as a failure: the text that did arrive is good.
* **Fix: the folder icon could fail silently on Windows.** `RevealDirectory` forgave every error, not just explorer.exe's habit of exiting 1 when it has in fact opened a window, so the failures that mean no window opened were swallowed too. That is the worst result a button can produce: nothing happens and nothing is said. Only the exit code is forgiven now.

## v0.37.0

Ten things reported from real use. Each was reproduced against the code before it was touched; one of the ten turned out to already work, and the change there is to say so on screen.

* **Fix: Esc did nothing while a bash command was running.** `exec.CommandContext` kills the process it started and nothing else, and the tool call does not return until every holder of the output pipe lets go of it — so one backgrounded child kept the turn blocked for that child's whole lifetime. Measured before the fix: cancelling `sleep 30 & sleep 30` returned after 30.0s, with the shell itself already reported as killed half a second in. The command now runs in a process group of its own and the whole group is killed, with a one-second backstop for anything the kill does not reach. A cancel also stops the remaining tools in a multi-tool step instead of running them anyway.
* **Fix: a turn could fail with "maximum context length" while the meter read half full.** What overflowed was not the history — it was the history *plus the output the request reserved room for*. A `max_tokens` of 64000 against a 131072-token window refuses every turn from 67k of history onwards, and automatic compaction never fires because it watches a number that says 53%. Requests are now sized against what is left of the window, and a request refused anyway is recovered from rather than ending the turn: the conversation is summarized and the turn retried, once, with a line in the transcript saying so.
* **Fix: a tool result could overflow the window on its own, and nothing downstream could help.** `read_file` on a large file put the whole file into the conversation, and `bash` returns whatever the command printed, so one `cat` of a log could exceed the entire context window inside a single message — the one shape no recovery can fix, since summarizing sends that message again and dropping older messages cannot drop the one that just arrived. A tool result is now capped at a quarter of the window, keeping the start and the end and saying in the middle what it left out, so the model knows to read the file in ranges. Applied to what is stored as well as what is sent, so the transcript, the event log and the model all agree.
* **Fix: a second overflow after a successful summary ended the session.** The recovery was one attempt, so the next message failed the same way and every one after it. Summarizing twice is the wrong answer — if the summary did not fit, length is not the problem — so the second attempt stops negotiating and forces the history to fit: it drops from the front, and cuts into the remaining messages if dropping is not enough. Unlike summarizing, it cannot fail. The size it aims for is taken from the conversation's own measured size, not from the window, because the character-count estimate runs about 4x low on Korean and Japanese — a history the server calls 90k measures 25k here, so a budget taken from the window alone would decide the request already fits, cut nothing, and lose the turn on exactly the conversations this exists for.
* **Fix: `/compact` could still fail for being too long — the one failure it cannot have,** since being too long is why anyone runs it. It sized its own request from the character estimate and sent it once, so when the server disagreed the answer was "compaction failed: ... maximum context length" and the session had nothing left to try. It now shrinks and re-sends, each attempt aiming at two thirds of what the conversation actually measures, so it converges on a size the server accepts instead of arguing with it. The same shrinking backs the turn loop, which no longer stops after a fixed two attempts. On a session where the server counted 10x what this side estimated, the turn found its way through in nine requests instead of dying on the second.
* **Fix: the recovery above still looked like a failure.** The loop handles the overflow and keeps going, but the notice it writes travels as an error event, and both clients treat any error event as the end of the turn — the activity light went out and a red failure appeared over a session that was still working and about to answer. A handled condition is a note in the transcript now, and the turn carries on visibly. An error nobody handled still stops the turn and still shows red.
* **Fix: a slash command typed while a turn was running did nothing at all in the Web UI** — no request, nothing queued, no message, the text still sitting in the box. It cannot be handed to the running turn (mid-turn text goes straight to the model, so `/compact` would arrive as four words of chat), so it is refused out loud now, the way the TUI has always done it.
* **Fix: `/compact` failed in exactly the situation it exists for.** It summarized by sending the whole conversation — the one thing already known not to fit — so an overflowing session answered "compaction failed: ... maximum context length is N tokens". Automatic compaction failed the same way, silently. The summarization request is now trimmed to fit, and says in the prompt what had to be left out.
* **Fix: the context meter read 5x low on every million-token Claude model.** Opus 5, Opus 4.8/4.7/4.6, Sonnet 5, and Sonnet 4.6 all have a 1M-token window; the lookup matched them on the family name and reported 200k. Automatic compaction watches that number, so a conversation was being summarized a fifth of the way in, over and over, with the real limit nowhere in sight.
* **Fix: `context_window` only reached one of the three things that read it.** The meter and the 80% compaction trigger still guessed from the model name while only the request sizing read the setting, so configuring it fixed the request and left the meter reporting a window that wasn't there. One resolution now feeds all three.
* **New: `context_window` on a model profile.** Local servers host anything under any name, and the guess for an unrecognised one is 128k. Guessing high is the harmful direction, since this number is what keeps a request inside the limit.
* **Fix: coming back to a conversation showed the end of the last answer and nothing above it.** The transcript is built from streamed text fragments — one per few characters — and the replay window is counted in events, so a single long reply filled it. Replies that have already finished are now replayed whole instead of fragment by fragment (the log has both), which is both the fix and considerably less work for the browser.
* **Fix: dictation stopped mid-sentence.** Three causes: any single failed chunk switched the microphone off, a long transcription made the session look abandoned so the daemon closed it underneath the microphone, and audio queued behind a slow request went one chunk per round trip and fell further behind the longer it ran. A hiccup is now retried with the same audio, a session closed by the daemon is reopened and dictation carries on, and a backlog goes as a single request.
* **Fix: the workspace path could only be picked, not typed.** Clicking the workspace went straight to the OS folder picker wherever there was one — so the desktop build, the only build with a picker, was the only build with no way to paste a path. It opens a box now, with Browse beside it.
* **New: a folder icon beside the workspace** opens that directory in a Finder/Explorer window. Offered only where the daemon is on the machine with the screen, same rule as the folder picker.
* **Fix: "a turn is in progress" with no way to find it.** The working directory is one process-wide thing, so a turn in *any* session refuses a workspace change — including one nobody is watching, and including one parked forever on an unanswered permission request. The refusal now names those sessions and offers to stop them and try again.
* **New: background tasks can be watched.** A task reported three words about itself — its agent, its id, and "running" — and nothing else, ever, because its own conversation is a session nothing listed and nothing opened. The panel now says which tool it is in, and clicking it opens its transcript live, with a stop button.
* **Forking already did the right thing, and now says so.** The new session is the copy, named "fork of X", and the original is untouched — but a fork is a verbatim copy, so the two transcripts read identically and neither said which was which. The fork's transcript now opens with a line naming what it was forked from.

## v0.34.0

Four findings about stored data and one about a credential. Each was reproduced before it was fixed, and two came back different from the review.

- **Fix: one large tool result could corrupt a session's log at the next restart.** The log was read back with a reader that has a maximum line length, and nothing truncates tool output, so a single `cat` of a large file writes a longer line — at which point reading stops in a way indistinguishable from reaching the end of the file. ## v0.33.2

**Security fix. Upgrade.**

- **Fix: an allowed command could carry an arbitrary second command past the permission check.** The bash line is split into segments so that each one has to earn "allow" on its own — but the splitter treated a backslash-escaped quote as opening a quoted region, and bash does not. So `git status \" && rm -rf ~` came out as a single segment, matched the built-in `git *` allow rule, and ran with no prompt, while bash executed the `rm`. Any allowed prefix was a launch point for anything appended to it: the exact attack segment splitting exists to stop, and reachable by the model or by a prompt-injection payload in a file it reads. Backslash escaping now follows bash — outside quotes a `\` makes the next character literal, so it can neither open a quote nor act as a separator.
- **Fix: a session could break permanently and stay broken.** Bedrock's Converse API rejects both an empty message and two messages of the same role in a row, and conversation history persists — so one request in a bad shape meant every retry after it failed the same way, and restarting did not help. Three paths produced it: a provider error returning before the model's reply was recorded, cancelling a turn before the first token, and compaction (whose summary is a user-role message that the next prompt landed straight after, so *every* successful compaction was followed by a broken turn). Outgoing requests are now normalized — empty messages dropped, consecutive same-role messages merged so both texts still reach the model in order — and the sources are fixed too.
- **Fix: on Bedrock, compaction itself failed.** History routinely ends with a user-role message, since tool results are one, and the compaction instructions were appended straight after it. That is the one call that must not fail, being what rescues a session that has run out of context.

## v0.33.1

Five bugs in the speech engine v0.33.0 shipped. Each was found by review and confirmed with a test written to fail first.

- **Fix: the sentence you just finished could reappear under the one you are saying.** A partial transcription still in flight when the speaker paused landed in the *next* utterance, as grey text. ## v0.32.13

## v0.32.12

- **Fix: a reply could stop halfway and leave the turn running forever.** Every token of model output is one event, and delivery to a client was best effort with a 64-slot buffer: a client that fell behind for a moment had events dropped and was never told. So it lost the middle of the reply, and then lost the `turn.done` that clears the spinner, with no way to know either had happened. Sixty-four events is well under a second of a local model talking. ## v0.30.1

- **Fix: installing the Windows MSI over an existing version failed with error 2753**, "The installer has encountered an unexpected error installing this package… The error code is 2753". Retrying appeared to work, which is what made it look intermittent.
  * Cause: the WebView2 bootstrapper is run by a custom action that reaches it through the MSI **File table** (`FileKey`). Windows refuses such an action — error 2753, "The File is not marked for installation" — whenever the referenced file's component is not part of the current install. On an upgrade that is exactly the situation: the bootstrapper is already on disk from the previous version, so file-versioning rules decide it doesn't need replacing. The retry "worked" only because the first attempt had already removed the old product, leaving the file genuinely absent and therefore due for installation.
  * Fix: the action is now conditioned on `$WebView2BootstrapperFile=3` — run only when that component is actually being installed in this transaction. Skipping is correct rather than a workaround: if the bootstrapper isn't being installed, an earlier install already ran it and the runtime is present. Fixing it from the other end isn't possible here — wixl hardcodes `RemoveExistingProducts` to run right after `InstallValidate` and doesn't implement WiX's `MajorUpgrade/@Schedule`.
  * **`package-msi.sh` now verifies the built MSI's tables** and fails the build if the WebView2 file, the custom action, its exact type, or the resolved condition is missing. Two silent breakages have shipped from this file already — a custom action wixl couldn't express (it warned and still exited 0, leaving the table empty), and now a condition mangled by the preprocessor. The build machine can't run Windows, so inspecting the database is the only feedback available.
  * Caught while writing that check: wixl's preprocessor **consumes a lone `$` and emits nothing**, so `$WebView2BootstrapperFile` reached the MSI as `WebView2BootstrapperFile` — an undefined property, making the condition always false and disabling the runtime install silently. It has to be written `$$` in the .wxs. The verification step catches this specific mistake by name.

Clients clear their waiting state and drain the prompt queue on `turn.done`, `turn.cancelled`, or `error`, never on `message.part.end`.
  * Belt and suspenders: if a send still reaches a busy daemon (a race, or a turn another client started on the same session), the 409 is turned into a queued prompt with a `[queued]` line instead of a red error, and it goes out on the next `turn.done`. The client library now exposes the HTTP status as a typed error for this.
  * Update the daemon and clients together: a new client attached to an older daemon never receives `turn.done` and will not clear its waiting state.

## v0.23.0

- **Fix every shell execution failing on Windows.** The bash tool, hooks, and custom-command `` !`shell` `` expansion all hardcoded `sh -c`, so on a Windows machine without Git Bash on PATH the model could not run so much as `git pull`: every call died with `exec: "sh": executable file not found in %PATH%` and the agent kept asking the user to run commands by hand.
  * New `internal/shell` package resolves the shell once per process: `sh` on PATH first (Git for Windows), then `bash.exe` at Git's usual install locations for installs that never touched PATH, then `cmd /c` as the always-present last resort. WSL cannot be selected by accident, since it ships `bash.exe` but never `sh.exe` and its install paths are not probed.
  * Under the `cmd` fallback, the bash tool's description tells the model it is talking to `cmd.exe`, so it writes cmd syntax instead of bash-isms that would fail confusingly.
  * Non-Windows behavior is unchanged: plain `sh -c` as before, covered by a regression test.

## v0.22.0

- **Auto-delegate matching prompts to a cheaper sub-agent**, so small lookups do not cost a model switch. New `auto_delegate` config block (`enabled`, `agent`, `match` globs) plus a runtime toggle, `/config auto_delegate on|off`, alongside `auto_compact` and `show_tps`.
  * The point is prompt-cache economics, not the per-token price. A cache entry is keyed by model as well as prompt bytes, so switching the session's model mid-conversation discards the entire cached prefix (tools, system prompt, every prior turn) and rewrites it at 1.25x (5m TTL) or 2x (1h TTL), against a 0.1x read. Delegation avoids that: the sub-agent runs in its own session, so the main session's model and prefix never change.
  * The delegated turn is visible as `[delegated to <agent>]` in both clients, and both halves of the exchange enter the main history so the main model has it as context next turn.
  * Guards: commands, skills, and `exit`/`:q` are resolved before the delegation check; an empty `match` list delegates nothing; a session that already has a parent never delegates again; an agent never delegates to itself. Off unless configured, so existing setups are unchanged.
  * `GET /api/settings` and the `config.changed` event now carry `auto_delegate`.
  * docs/USAGE.md gained a "Choosing what to delegate" section: the one decision to make (which questions may be answered at lower quality), a read-only vs produces-or-changes rule of thumb, and a start-narrow-then-widen loop.

## v0.20.0

- **git commands run without asking.** Any `git` subcommand through the `bash` tool is auto-allowed by default, no config needed. This is only safe because of a hardening fix landing in the same release: a `bash` permission rule now resolves per command rather than as one raw string, so `git status && rm -rf ~` can no longer ride an allowed `git *` prefix — the line is split on `&&`, `||`, `;`, `|`, and newlines (quote-aware, so a separator inside a commit message is left alone), every segment has to earn `allow` on its own, and any `deny` anywhere denies the whole line. "Allow for session" remembers the grant in memory for the rest of that session. "Always allow" does that and also writes a matching rule to config.json (only the `permission` key is touched; every other key is preserved byte for byte), so the same pattern is auto-allowed in future sessions too. For `bash`, the granted rule generalizes to the command's first word (`npm test` grants `npm *`); other tools grant the exact subject. Session grants are cleared when a session is deleted or the daemon restarts.
- **Esc cancels the running turn**, in both the TUI and Web UI. The daemon now tracks a per-session cancel function and exposes `POST /api/sessions/{id}/cancel`; cancelling records a `turn.cancelled` event (not an error) and clears the session's busy flag so the next message isn't refused. Cancelling also drops anything waiting in the prompt queue, since the point of cancelling is to stop.
