# Changelog

## v0.31.0

- **A structural refactor across every major package** (config, agent, daemon, cmd/localcode, TUI, Web UI), done phase by phase against the full existing test suite so no behavior changed except the specific bugs below. Every large file was split by concern into focused ones — nothing here is a rename for its own sake; each split paired with either a real bug fix or a genuine simplification. See `docs/REFACTORING.md` for the full plan and phase-by-phase rationale.
- **Nine real bugs found and fixed during the refactor, each pinned by a new regression test:**
  * **Fix: a project-scope `.localcode/config.json` was silently ignored** whenever a global config also existed — `Config.merge` copied only a few top-level fields and dropped `mcp_servers`, `permission`, `auto_delegate`, and `skip_permissions` from the project file entirely. `localcode mcp add --scope project` (and hand-edited project configs) now actually take effect.
  * **Fix: `config.json` writes were not atomic and could corrupt the file on a crash mid-write.** All five writers (MCP servers, permission rules, skip-permissions, auto-delegate) now go through one `os.CreateTemp` + `os.Rename` primitive at `0600`, and the one writer that was missing `os.MkdirAll` (`RemovePermissionRuleFromFile`) no longer fails on a fresh project.
  * **Fix (TUI): an `error` event whose payload wasn't a string left the busy spinner running forever**, with no way to recover short of restarting. Turn teardown (`waiting=false`, clear the running-tool indicator) is now unconditional for every turn-terminating event, including a malformed one.
  * **Fix (TUI): typing a slash command, or `exit`/`:q`, while a turn was streaming silently did nothing** — the input cleared but nothing queued, nothing sent, and `exit` didn't quit. `exit`/`:q` now works mid-turn, and an unqueueable command explains why instead of vanishing.
  * **Fix (Web UI): a task's agent name or status, taken verbatim from an SSE payload, was spliced into `innerHTML` unescaped** — the one XSS gap in the file. `renderTasks` (now `render.js`) builds rows with `createElement`/`textContent` like every other listing already did.
  * **Fix (Web UI): a bare number on its own line after a fenced code block could corrupt the rendered reply.** The markdown renderer's code-block placeholder was a plain digit sequence (` 3 `), which collided with model output that happened to contain one — silently splicing in the wrong code block, or the literal string `undefined`. The placeholder is now a `\u0000`-delimited sentinel no model output can type.
  * **Fix (Web UI): `/help` displayed one line double-escaped** (`&lt;skill name&gt;` instead of `<skill name>`) because that one entry in the help text was pre-escaped while the rest weren't, and the whole block was escaped again at render time. Help text is now rendered as text nodes, never HTML strings, so there is nowhere left for a line to be escaped twice — or forgotten.
  * **Fix (TUI): a failed `GET /api/agents` or `GET /api/commands` left Tab silently dead**, with no explanation anywhere. Both failures now set the status line's error message.
  * **Fix (CLI): the four `--scope` parsers in `localcode mcp` disagreed on unknown flags** — `mcp add` rejected them, `mcp add-json`/`mcp remove` silently treated `--bogus` as a positional argument instead. All four now share one parser with one behavior.
- **The TUI transcript no longer fights you when you scroll up mid-reply.** It used to force the view back to the bottom on every single streamed event, so reading something further up while a reply was still coming in was impossible. The transcript is now structured data (`[]transcriptEntry`, styled only at render time) instead of a pre-rendered ANSI string, which is what makes this fixable: the viewport now only auto-follows the bottom when it was already there.
- **A dependency-free JavaScript test suite for the Web UI** (`test/webui/`, 87 tests) — the one part of the program that had no automated coverage before this release. It runs the real shipped `internal/daemon/static/js/*.js` files (a hand-written DOM plus Node's built-in test runner and `vm.SourceTextModule`, no `npm`, no bundler, no new dependency) and is what made the Web UI bug fixes above safe to verify without a browser open. `make test-js`, or `go test ./internal/daemon/` (skips itself if `node` isn't installed).
- **The Web UI is now native ES modules** (`internal/daemon/static/js/*.js`, 14 files with explicit ownership — state, API, rendering, modals, commands, events — instead of one 1531-line script) instead of one file, loaded via `<script type="module">` with no bundler and no Go changes to the embedded-filesystem serving.

## v0.30.1

- **Fix: installing the Windows MSI over an existing version failed with error 2753**, "The installer has encountered an unexpected error installing this package… The error code is 2753". Retrying appeared to work, which is what made it look intermittent.
  * Cause: the WebView2 bootstrapper is run by a custom action that reaches it through the MSI **File table** (`FileKey`). Windows refuses such an action — error 2753, "The File is not marked for installation" — whenever the referenced file's component is not part of the current install. On an upgrade that is exactly the situation: the bootstrapper is already on disk from the previous version, so file-versioning rules decide it doesn't need replacing. The retry "worked" only because the first attempt had already removed the old product, leaving the file genuinely absent and therefore due for installation.
  * Fix: the action is now conditioned on `$WebView2BootstrapperFile=3` — run only when that component is actually being installed in this transaction. Skipping is correct rather than a workaround: if the bootstrapper isn't being installed, an earlier install already ran it and the runtime is present. Fixing it from the other end isn't possible here — wixl hardcodes `RemoveExistingProducts` to run right after `InstallValidate` and doesn't implement WiX's `MajorUpgrade/@Schedule`.
  * **`package-msi.sh` now verifies the built MSI's tables** and fails the build if the WebView2 file, the custom action, its exact type, or the resolved condition is missing. Two silent breakages have shipped from this file already — a custom action wixl couldn't express (it warned and still exited 0, leaving the table empty), and now a condition mangled by the preprocessor. The build machine can't run Windows, so inspecting the database is the only feedback available.
  * Caught while writing that check: wixl's preprocessor **consumes a lone `$` and emits nothing**, so `$WebView2BootstrapperFile` reached the MSI as `WebView2BootstrapperFile` — an undefined property, making the condition always false and disabling the runtime install silently. It has to be written `$$` in the .wxs. The verification step catches this specific mistake by name.

## v0.30.0

- **Fix: the Windows desktop build sprayed console windows across the screen.** `localcode-gui.exe` is linked as a GUI-subsystem binary, and a process with no console of its own makes Windows allocate a brand new console — with a visible window — for every *console* child it starts. localcode starts them constantly: one per stdio MCP server at launch, one per bash tool call, one per hook, one for the `git rev-parse` that locates the memory directory. Several black boxes appeared right after launch and another on every shell command.
  * New `internal/childproc`: `Hide(cmd)` sets `CREATE_NO_WINDOW` so a child gets a console with no window, and is a no-op everywhere but Windows. Applied at all five spawn sites. Nothing about how children are used changes — their stdio is always wired to pipes and none of them ever wanted a terminal.
  * A source-scanning test (`TestEverySpawnSiteHidesItsWindow`) fails the build if a function calls `exec.Command` without `Hide`, with an explicit exemption list. This symptom only shows up on Windows in the GUI build, so nothing in a normal dev loop or in CI's headless smoke check would catch a new spawn site that forgot it; the guard was itself verified by planting a spawn site and watching it fail.
- **Auto-delegation is fully configurable from the GUI: which prompts, and which agent answers them.** The pill under the prompt box now opens a panel with the on/off switch, an agent picker listing each agent with the model it resolves to (so the cost trade-off is visible where the choice is made), and an add/remove list of match patterns. Previously only the on/off switch was reachable, and the target agent and patterns had to be hand-edited into config.json.
  * Every change applies to the very next prompt and is written back to config.json. Each control rewrites only its own field, so toggling off and on can't lose the target, and editing patterns can't flip the switch. A config with no `auto_delegate` block can be configured from scratch.
  * `POST /api/settings/auto-delegate` now takes `enabled`, `agent`, and `match` as optional pointers, so the pill and the panel post different subsets of one endpoint. An unknown agent is rejected before anything is applied. `GET /api/settings` reports `auto_delegate_match` alongside the agent.
  * `Config.AutoDelegate` is now read through `AutoDelegateSnapshot()` under a mutex. It was read unguarded from the turn goroutine, which was safe only as long as nothing could change it at runtime — which is exactly what this feature adds.
  * Verified end to end: a prompt matching a pattern added from the panel was answered by the chosen agent's model on the next turn (`[delegated to explore]` → the cheap model) while a non-matching prompt went to the session's own, changing the target agent mid-session took effect immediately, and both the runtime state and config.json agreed throughout.

## v0.29.0

- **Remote MCP servers are supported, so `mcp import-claude` no longer skips them.** Until now only stdio servers could be represented, and a url-based entry in a Claude Code config was counted and dropped — which meant the import silently left behind exactly the servers that are hardest to set up by hand. All three MCP transports now connect: `stdio` (a local child process), `http` (streamable HTTP), and `sse` (the older HTTP+SSE).
  * `MCPServerConfig` gained `type`, `url`, and `headers`, matching Claude Code's own field names so an entry copies across verbatim. `type` may be omitted: an entry with a `url` infers `http`, anything else `stdio`, so every existing stdio config keeps working untouched and is still written in its old shape.
  * `headers` is how an auth token reaches a remote server. The SDK's transports expose no header field, so this goes through a `RoundTripper` that adds them — only when absent, so a config entry can't clobber a header the protocol itself controls. Header **values are never printed** by `mcp list` or `mcp get`, only key names.
  * Remote servers get no whole-request timeout (a tool call may legitimately run long) but a 60s response-header timeout. Deliberately not `http.Client.Timeout`, which also covers reading the body and would tear down the long-lived SSE streams both remote transports keep open.
  * `localcode mcp add --transport http|sse <name> <url>` registers one, with `-H "Key: Value"` (repeatable) for credentials; `add-json` accepts either shape. Config validation now rejects a half-written entry (stdio with no command, remote with no url, a non-http scheme) at startup with a clear message instead of at connect time.
  * Verified against a real MCP server over both remote transports: tools list and call correctly, a server requiring an `Authorization` header is reachable with it configured and fails without it or with a wrong token, and a Claude Code config containing http/sse/bare-url entries imports and connects end to end.
- **`localcode mcp list` is one line per server.** It now prints just the name, scope, and connection status — the config file path, command line/url, and env/header key names are gone, since a status view shouldn't require reading four lines per server to find the one that's down. `mcp get <name>` remains the full definition.

## v0.28.0

- **Switching sessions now moves the workspace with them.** Each session already recorded the directory it was created in; selecting one now also switches the daemon's working directory to it, so reopening a conversation about another project puts you back in that project instead of leaving its transcript pointed at wherever you happened to be. A `[workspace] <path>` line marks it in the transcript, since it changes where every later tool call and bash command resolves from. Sessions with no recorded workspace (written before the field existed) leave it alone rather than guessing, and a refused switch — another session mid-turn, or a directory since deleted — is reported without blocking the session switch itself.
- **Clicking the workspace in the desktop window opens the OS folder picker** instead of a box to type an absolute path into. New `internal/dialog` package, deliberately pure Go: it shells out to `osascript` (macOS), a WinForms `FolderBrowserDialog` via PowerShell (Windows), or zenity/kdialog (Linux), rather than binding a native toolkit — the GUI already carries one CGo dependency that can't be cross-compiled, and a second one would push that cost onto the plain daemon and TUI builds too. Paths are passed to the helpers as AppleScript string literals or environment variables, never interpolated into a command line.
  * The picker is wired up **only** in desktop-window mode (`daemon.PickDirectory`, nil everywhere else): a daemon reached over the network would open its dialog on the server, in front of nobody. `GET /api/workspace` reports `can_browse` so the browser keeps the typed-path box, which is also the only option the web platform allows — neither `<input webkitdirectory>` nor `showDirectoryPicker()` hands back a real filesystem path.
  * New `POST /api/workspace/browse`. It only *picks*: applying is still the existing `POST /api/workspace`, so a chosen directory can still be refused mid-turn and reported as such. A dismissed dialog is 204, not an error. The dialog is tied to the request context, so closing the window takes the helper process down with it instead of orphaning it.
- **Panel colors.** The side panels and the surrounding chrome are now rgb(24,24,24) and the transcript column rgb(32,32,32), replacing the blue-tinted near-black; raised surfaces (prompt box, code blocks, agent dropdown) get their own one-step-lighter grey so they still read as raised against a transcript that is no longer darker than they are.
- **The session list moved to its own panel on the left, and each entry shows the workspace it belongs to.** Clicking anywhere on a session card switches to it — previously switching was a small `switch` button inside a section buried under two others in the right panel, which made the most common action the smallest target on the row. Each card now shows the session's title, the directory it was created in (shortened from the front, full path in the tooltip), and its creation time. The agent name is gone from the card: it's a property of the next message, not of the session's identity, and both the header dropdown and the status bar already carry it. `rename`/`delete` still act per-session without switching.
  * New `Session.Workspace` field, stamped at creation from the daemon's live workspace and persisted in `<id>.meta.json`, so it survives a restart. It is never rewritten afterwards — [switching the workspace](USAGE.md#switching-the-workspace-directory) changes where *new* sessions start rather than relabelling old ones, since the whole point of the field is to say which project a conversation belongs to. Sessions written by an older build have no workspace and show `(workspace not recorded)`. `Store.CreateSessionIn` takes the workspace; `CreateSession` still exists and records none.
- **`localcode mcp list` now tests each connection.** Being registered in config.json says nothing about whether a server's command exists, starts, or speaks MCP — the old listing could only ever repeat the file back. Each server is now started for real, handshaked, asked for its tools, and shut down, printing `connection: OK (N tool(s): ...)` or `connection: FAILED — <reason>` under its entry, plus a failure count at the end. A failure is reported rather than returned as an error, since the listing itself succeeded. Each check is bounded by a 20s timeout so an unresponsive server delays the listing instead of hanging it (verified against a server that never answers). `--no-test` skips the connecting for the old, instant behavior. New exported `mcp.Ping`.
- **Tab switches agent in the Web UI and GUI window**, matching the TUI, instead of walking the browser's focus ring around the page. `Shift+Tab` goes back. Focus stays in the prompt box; inside a modal Tab still moves between fields, which is the only thing it could usefully mean there.
- **Model names are visible where the agent is chosen.** The header dropdown lists each agent as `name (model)` with the description moved to the tooltip, and the status bar under the prompt now shows the model from the moment a session opens — resolved from the agent's profile via `GET /api/agents` — instead of staying blank until the first reply came back and reported one. A reported model still wins over the configured one, since they differ when a profile is overridden server-side.
- **The activity light means three specific things now**: gray = no live connection to the model (the SSE stream to the daemon is down), solid green = connected and idle, blinking green = the model is running your prompt. The old scheme pulsed amber while working and flashed green *after* a reply, which left the two questions people actually ask — "is it up?" and "is it working?" — sharing one indicator and answered by color alone. It recovers to green on its own once a stopped daemon comes back.
- **Auto-delegation is togglable from the prompt bar**, not just `/config auto_delegate on|off`. The `auto-delegate: on|off` pill applies the change to the running loop immediately (verified: the very next matching prompt was delegated, no restart) and writes it back to config.json. Only the `enabled` field is rewritten — the `agent` and `match` you configured are left exactly as they were, so toggling off and on again can't quietly reduce the block to an inert one. With no `auto_delegate` block at all the pill reads `on (unconfigured)` rather than showing a bare "on" that delegates nothing. New `POST /api/settings/auto-delegate`, `config.SetAutoDelegateEnabledInFile`, and `auto_delegate_agent` in `GET /api/settings`.
- **`localcode-gui.exe` hands the cmd prompt back.** It is now linked with `-H windowsgui`, so launching it from a console opens the window and returns immediately instead of pinning the console for the window's whole lifetime (and from Explorer it no longer flashes an empty console box). The trade-off: a GUI-subsystem process has no console, so the console-only subcommands (`version`, `mcp`, `login`) print nowhere useful from that binary — they belong to `localcode.exe`, which the same MSI installs. The CI smoke check uses `Start-Process -Wait -PassThru` so the exit code is still observed now that PowerShell no longer waits on it.

## v0.27.0

- **GUI launches directly, no `--gui` needed.** A build made with `-tags gui` now defaults `--gui` to on, so `./localcode-gui` opens the native window immediately. Pass `--gui=false` to force the TUI on that same build. A plain (non-gui) build is unaffected: `--gui` still defaults to off and returns the same explanatory error as before.
- **Model output renders as markdown**, in both the Web UI and the native GUI window (same page). A small dependency-free renderer handles headers, bold/italic, inline code, fenced code blocks, lists, blockquotes, links, and rules; everything else streams as plain escaped text, so nothing the model writes can inject markup. Streamed text now accumulates per-message and re-renders on each delta rather than growing a single flat text node, which is also what makes an in-progress code fence render sanely mid-stream.
- **Permission status is visible under the prompt, and editable by clicking it** — in the Web UI and the GUI window alike, since they're the same page. The pill shows `permissions: ask (N rules)` or `permissions: skip`; clicking it opens a panel to toggle `skip_permissions` and add or remove individual allow/ask/deny rules, all applied immediately and written to config.json. New endpoints: `GET /api/settings` now also reports `skip_permissions`, `permission_rules`, and `can_edit_permissions`; `POST /api/permissions/skip`, `POST /api/permissions/rules`, and `POST /api/permissions/rules/remove` make the changes. `Config.Permissions` and `SkipPermissions` are now guarded by a mutex, since these can change at runtime while a tool call on another goroutine is resolving a decision.
- **Fix: a permission prompt no longer swallows or misroutes what you type.** Previously, typing while a permission request was pending either queued as a bogus follow-up prompt (Web UI: `waiting` stayed true with no way to tell the difference from "the model is thinking") or was silently dropped (TUI: Enter was a no-op with no explanation). The Web UI now locks the prompt box while a permission modal is open, with a placeholder pointing at it; the TUI prints a one-time hint the first time Enter is pressed while a request is pending. Permission descriptions that come back empty now show `(no description given)` instead of a blank line, in both clients.
- **Workspace directory shown at the top of the GUI window (and the Web UI header), with a click-to-change control.** localcode has always resolved every relative file path and bash command against the process's working directory, set once at startup; there was no way to see or change it without restarting. New `GET /api/workspace` / `POST /api/workspace`: the latter validates the target is a real directory, refuses while any session has a turn in flight (switching mid-tool-call would silently redirect it partway through), then `os.Chdir`s and updates `Loop.ProjectDir` together so both tool path resolution and custom-command `` !`shell` ``/`@file` expansion agree on the new directory. This is process-wide, not per-session — one workspace at a time, like opening a different folder in an editor.
- **`localcode mcp import-claude`** pulls an existing Claude Code setup's MCP servers into localcode's config.json: this project's checked-in `./.mcp.json`, plus `~/.claude.json`'s global servers and its per-project block for the current directory (project-scoped entries win on a name collision, matching Claude Code's own precedence). Only stdio servers (`command`/`args`/`env`) can be represented; url-based remote servers are detected and skipped with a count, not silently dropped. Re-running it overwrites a server already registered under the same name with the freshly imported definition by default, since that's the common case (the Claude Code side changed); `--skip-existing` opts back into leaving those alone. `-s global|project` picks the target scope, same as `mcp add`.

## v0.25.0

- **Tool activity moved out of the conversation and into a live indicator.** `[tool] running bash...` / `[tool] done` / `[task] ...` lines no longer appear in the transcript. Instead, while anything is running, a line below the prompt box animates and says what is happening: the running tool's name, the prompt-queue depth, and the number of background tasks. It clears at the turn boundary, however the turn ends (`turn.done`, `turn.cancelled`, or an error). The Web UI carries the same information in its status bar.
- **Background tasks are visible and inspectable.** A running task shows in that indicator, and two new commands cover the detail: `/tasks` lists every task in the session with status, agent, and prompt (client-side, no model call), and `/tasks <id>` shows everything that task has produced so far. It reads the task's event log, so it works mid-run as a progress view rather than only a post-mortem. New endpoint `GET /api/tasks/{id}/output`.
- **A background task no longer blocks the prompt.** Tasks run in their own child sessions, so the parent session is idle: a prompt typed while only a task is running now sends immediately instead of sitting in the queue. Only a turn in the same session queues what you type.
- **Fix multi-line paste rendering as a blank black block in the TUI.** The paste arrives while the prompt box is still one row tall, so the textarea scrolls down to keep the cursor visible; the box then grows, but bubbles' `repositionView` only ever scrolls to bring the cursor *into* view and never back up once everything fits. The stale offset hid the first lines and painted the rows past the end black on black, while `Value()` stayed correct, which is why sending the text worked. The prompt box is now scrolled back to the top whenever the whole value fits, preserving the cursor.
- Docs: README's feature table was three releases stale (no auto delegation, no running indicator, no `/tasks`, no Up/Down recall or Esc, no Windows shell resolution, and a permissions row that predated the per command bash checking and the always allow prompt). IMPROVEMENTS.md still listed two items as outstanding that had already shipped: coarse bash permission globs (fixed in v0.20.0) and "always allow" on permission prompts (v0.20.0). USAGE.md's known limitations still claimed two clients on one session can interleave turns, which v0.24.0 fixed; the remaining gap is `/compact` overlapping a turn, and it now says that instead.
- **New `skip_permissions` setting**, the equivalent of Claude Code's `--dangerously-skip-permissions`: every `ask` becomes `allow`. Defaults to **off** and must be opted into deliberately, since with it on the model writes files and runs shell commands with no confirmation. Explicit `deny` rules still deny, so a rule written to forbid something keeps forbidding it.

## v0.24.0

- **Fix prompts typed during tool execution erroring with 409 instead of queuing.** `message.part.end` fires once per model message, and a turn with tool calls streams several (the pre-tool text, then the post-tool answer), so both clients treated the first one as the end of the turn, skipped the queue, sent immediately, and bounced off the daemon's busy flag with `409: session is already processing a message`.
  * The daemon now emits a `turn.done` event as the real turn boundary, appended only after the busy flag is cleared, so a message sent the instant a client sees it can never 409. Clients clear their waiting state and drain the prompt queue on `turn.done`, `turn.cancelled`, or `error`, never on `message.part.end`.
  * Belt and suspenders: if a send still reaches a busy daemon (a race, or a turn another client started on the same session), the 409 is turned into a queued prompt with a `[queued]` line instead of a red error, and it goes out on the next `turn.done`. The client library now exposes the HTTP status as a typed error for this.
  * Update the daemon and clients together: a new client attached to an older daemon never receives `turn.done` and will not clear its waiting state.

## v0.23.0

- **Fix every shell execution failing on Windows.** The bash tool, hooks, and custom-command `` !`shell` `` expansion all hardcoded `sh -c`, so on a Windows machine without Git Bash on PATH the model could not run so much as `git pull`: every call died with `exec: "sh": executable file not found in %PATH%` and the agent kept asking the user to run commands by hand.
  * New `internal/shell` package resolves the shell once per process: `sh` on PATH first (Git for Windows), then `bash.exe` at Git's usual install locations for installs that never touched PATH, then `cmd /c` as the always-present last resort. WSL cannot be selected by accident, since it ships `bash.exe` but never `sh.exe` and its install paths are not probed.
  * Under the `cmd` fallback, the bash tool's description tells the model it is talking to `cmd.exe`, so it writes cmd syntax instead of bash-isms that would fail confusingly.
  * Non-Windows behavior is unchanged: plain `sh -c` as before, covered by a regression test.

## v0.22.0

- **Auto-delegate matching prompts to a cheaper sub-agent**, so small lookups do not cost a model switch. New `auto_delegate` config block (`enabled`, `agent`, `match` globs) plus a runtime toggle, `/config auto_delegate on|off`, alongside `auto_compact` and `show_tps`.
  * The point is prompt-cache economics, not the per-token price. A cache entry is keyed by model as well as prompt bytes, so switching the session's model mid-conversation discards the entire cached prefix (tools, system prompt, every prior turn) and rewrites it at 1.25x (5m TTL) or 2x (1h TTL), against a 0.1x read. Delegation avoids that: the sub-agent runs in its own session, so the main session's model and prefix never change.
  * The delegated turn is visible as `[delegated to <agent>]` in both clients, and both halves of the exchange enter the main history so the main model has it as context next turn.
  * Guards: commands, skills, and `exit`/`:q` are resolved before the delegation check; an empty `match` list delegates nothing; a session that already has a parent never delegates again; an agent never delegates to itself. Off unless configured, so existing setups are unchanged.
  * `GET /api/settings` and the `config.changed` event now carry `auto_delegate`.
  * docs/USAGE.md gained a "Choosing what to delegate" section: the one decision to make (which questions may be answered at lower quality), a read-only vs produces-or-changes rule of thumb, and a start-narrow-then-widen loop.

## v0.21.0

- **Up and Down recall previous prompts** in both the TUI and Web UI, the way shell history works.
  * Up walks back through prompts already sent, newest first. Down walks forward again.
  * Stepping forward past the newest entry restores the draft being composed before recall started, so reaching for history never eats unsent text.
  * Recall only triggers at the box's edges. The cursor has to already be on the first line for Up, and the last line for Down, so arrows still move the cursor normally inside a multi-line prompt.
  * Consecutive duplicates collapse to one entry.

## v0.20.0

- **git commands run without asking.** Any `git` subcommand through the `bash` tool is auto-allowed by default, no config needed. This is only safe because of a hardening fix landing in the same release: a `bash` permission rule now resolves per command rather than as one raw string, so `git status && rm -rf ~` can no longer ride an allowed `git *` prefix — the line is split on `&&`, `||`, `;`, `|`, and newlines (quote-aware, so a separator inside a commit message is left alone), every segment has to earn `allow` on its own, and any `deny` anywhere denies the whole line. Command substitution and output redirection (`$(...)`, `` `...` ``, `<(...)`, `>(...)`, `>`, `>>`) never auto-allow, since they can run or write to something the per-segment check can't see. See docs/USAGE.md's permission rules section.
- **Permission prompts now offer allow-for-session and always-allow**, alongside the existing allow-once and deny — `y`/`n`/`s`/`a` in the TUI, four buttons in the Web UI. "Allow for session" remembers the grant in memory for the rest of that session. "Always allow" does that and also writes a matching rule to config.json (only the `permission` key is touched; every other key is preserved byte for byte), so the same pattern is auto-allowed in future sessions too. For `bash`, the granted rule generalizes to the command's first word (`npm test` grants `npm *`); other tools grant the exact subject. Session grants are cleared when a session is deleted or the daemon restarts.
- **Esc cancels the running turn**, in both the TUI and Web UI. The daemon now tracks a per-session cancel function and exposes `POST /api/sessions/{id}/cancel`; cancelling records a `turn.cancelled` event (not an error) and clears the session's busy flag so the next message isn't refused. Cancelling also drops anything waiting in the prompt queue, since the point of cancelling is to stop.
